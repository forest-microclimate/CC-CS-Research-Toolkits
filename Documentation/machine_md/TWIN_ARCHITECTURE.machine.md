# ─── PREMISE (the difference trap) ─────────────────────────────────────────
FACT.two-toolkits: two toolkits sit side by side in this project — the Claude Code Research Toolkit (**CCRT**), which runs inside Claude Code, + the Claude Science Research Toolkit Bundle (**CSRTB**), which runs inside Claude Science. They carry the SAME research methodology: the same disciplines for planning work, for checking a claim against the record, + for writing so a reader can follow.
NOTE.locate-the-kit: a THIRD component rides beside the twin without being a third carrier — the portable **planner-kit**, shipped INSIDE the CC toolkit at `CCRT/planner-kit/`. It packages the per-project supervisory workflow, not the shared methodology, + installs SEPARATELY: the CCRT once into `~/.claude` (the global capability); the kit's own `install.sh` in EACH project root that adopts the workflow. Deliberately separate installers, designed to be used together.
FACT.they-differ: yet compared line by line they do not match — one has a guard that halts a bad write before it lands, the other has none; one counts more skills than its sibling; a role that lives as a standalone specialist on one side lives as a paragraph of inline guidance on the other.
TRAP.close-the-difference: the natural reaction to a difference is to close it — find a skill on one side with no twin + read it as a gap to port across; notice one toolkit carrying more skills + read the shortfall as incompleteness. That reaction is the MOST EXPENSIVE mistake you can make with this architecture, because most of those differences are NOT defects — they are the design. Acting on the wrong reading either manufactures work that should never be done or, worse, quietly drifts the two toolkits apart until the shared methodology they exist to protect no longer agrees with itself.
GOAL.this-guide: explains why the toolkit is built as a twin + hands you the few ideas that let you read any difference correctly ⇒ by the end you can look at any mismatch, name what kind of thing it is, + know what, if anything, it asks of you.
DEF.methodology: what is actually shared = the **methodology**, the intellectual content: the disciplines for decomposing + routing a job, checking a claim against the record instead of asserting it, + making prose stick. That content is single-sourced, authored once + carried twice; the only reason to carry it twice is the platform underneath.

# ─── §1 WHAT IT IS: ONE METHODOLOGY ON TWO PLATFORMS ───────────────────────
FACT.generative-fact: the entire architecture rests on a single fact about where the two toolkits run.
PLATFORM.code: **Claude Code is a local process** — a real shell, files under a folder you can list, hooks that fire on real events + can block an action before it happens, a local audio device, + subagents that run in the same working tree + each hand back one report.
PLATFORM.science: **Claude Science is a remote sandbox** — reaches you only through a browser, has no hooks + no local audio, hands work to isolated workers through an asynchronous software interface rather than a shared shell, + keeps state in an artifact store + a per-specialist memory instead of in files on a disk.
EX.one-discipline-two-lands: take one discipline + watch it land differently — both toolkits enforce the same rule: an agent may not claim a result it did not check. On Claude Code that rule is a HOOK: when an agent writes a claim that mismatches the record, the hook fires on the write event + blocks it before it lands. Claude Science has no hook surface for a hook to live on, so the identical discipline rides as a PROSE GATE in the planner's instructions + a background reviewer scores whether the agent honored it. Same job, same intent, two different machines — each is the discipline expressed in the only atoms its platform offers.
WHY.twin-not-simpler: this is why the toolkit is a twin + not something simpler. A SINGLE toolkit cannot run on both platforms, because the mechanisms are disjoint + the two runtimes do not co-exist. TWO INDEPENDENT toolkits would run fine, but the shared methodology would drift apart the first time a lesson landed on one side + not the other, + no one would notice until the two had diverged past reconciling. Carrying **one methodology on two carriers** threads between those failures: the intellectual content is written once, so it cannot fork, while each mechanism stays native to its platform.

# ─── §2 THE THREE TIERS ────────────────────────────────────────────────────
DEF.three-tiers: every load-bearing item in either toolkit classifies into exactly ONE of three tiers — the **shared tier**, the **split-mechanism tier**, + the **platform-only tier** (TIER-S, TIER-C, TIER-P in the map that owns the full definitions).
TIER-S.shared: same content + same KIND of carrier on both sides. A change to one should be MIRRORED to the other, allowing for local vocabulary. The platform-neutral methodology skills live here — the disciplines that carry the same meaning on either platform.
TIER-C.split-mechanism: shares its discipline across both sides but carries it in a DIFFERENT mechanism, because the platforms differ. The claim-checking rule above is exactly this: one discipline, a hook on one side + a prose gate on the other.
TIER-P.platform-only: meaningful on one platform + inapplicable on the other, so it NEVER crosses. EX: a local-audio alert has nothing to beep through on a browser-only sandbox; a sandbox's org-migration engine has no local object to act on.
WHY.three-not-two: the middle tier cannot fold into either neighbor without losing something. Fold TIER-C into TIER-S ⇒ you lose the standing warning never to copy its mechanism, so someone eventually pastes a hook into a file that cannot run it. Fold TIER-C into TIER-P ⇒ you lose the real obligation to mirror the change, so a shared lesson lands on one side + silently skips the other. The middle is IRREDUCIBLE.
WHY.tier-tag-buys: the tier tag is not a label, it is the item's MAINTENANCE DUTY written down. It heads off the two readings that cause the most damage — that "present on both sides" means "should be byte-identical" (FALSE for anything in TIER-C) + that "absent on one side" means "a gap to fill" (usually false).

# ─── §3 THE LAW THAT PROTECTS THE TWIN: NEVER BYTE-COPY ────────────────────
RULE.never-byte-copy: TIER-C carries one hard rule — WHEN a shared discipline changes on one side ⇒ RE-EXPRESS it in the other platform's atoms; you NEVER copy the mechanism across.
MAP.atoms-pair: the atoms pair up predictably — the Claude Code subagent tool ↔ the Claude Science delegation interface; a file ↔ an artifact; a hook ↔ a piece of prose or a small kernel of logic; an always-on rule ↔ a per-specialist clause.
EX.self-check-port: the planner's self-check is the worked example the toolkit itself points to. Claude Science gained a prose gate that has the planner re-read its own turn + emit a marker for the reviewer to score. When that same discipline was carried to Claude Code, the port did NOT paste the prose across — it added a single line pointing at the hooks that already enforce the check on Code, where a hook is the stronger form. The discipline arrived on both sides; the mechanism did not travel.
WHY.absolute: the reason the rule is absolute is what a byte-copy actually does — it drags one platform's runtime call into the other platform's file. A Science delegation call pasted into a Code file, or a Code hook pasted into a Science profile, cannot execute where it lands, + the discipline it was meant to carry does not fail LOUDLY. It fails SILENTLY, which is the failure the whole tier model exists to prevent.

# ─── §4 READING A DIFFERENCE CORRECTLY ─────────────────────────────────────
DIFF.absence: two kinds of difference tempt you most, both with a disciplined reading. FIRST = an ABSENCE: a skill on one side with no same-named twin on the other ⇒ treat it as a question with THREE answers, not a gap. It is in exactly one of three states: (1) already **ported under another name or carrier** — a Science skill can legitimately map to a Code rule or hook rather than a Code skill; if so, there is nothing to port, so you check the rules + hooks before concluding anything is missing. (2) **genuinely platform-only** — dependent on an object the other side does not have. (3) **an open port-candidate** — portable + not yet carried across.
RULE.default-port-candidate: you decide which before you act, + an unclassified item defaults to PORT-CANDIDATE, never silently to excluded, because a silent exclusion is indistinguishable from an oversight.
WHY.wrong-not-free: getting this wrong is not free — acting on the wrong reading either builds a DUPLICATE skill (a routing hazard, because an agent cannot tell which of two same-purpose skills to load) or spends effort re-porting something that already exists under another name.
DIFF.count: SECOND = a COUNT: the two rosters are different sizes, + the difference is expected, not a shortfall. Every delta is explained by the tiers already described — platform-only items that live on one side by design, roles carried in a different form on each side, mechanism asymmetries in TIER-C.
RULE.parity-not-a-signal: because the deltas are STRUCTURAL, aggregate parity is not a correctness signal — a matched pair of totals would tell you nothing, + a mismatched pair tells you only to classify, not to port. The current counts + full side-by-side belong to the roster guide (owns them, keeps them current); they drift as the toolkits grow, so the discipline is to RECOUNT from the trees before citing a number rather than trusting one copied into prose.

# ─── §5 WHY A ROLE SITS WHERE IT SITS ──────────────────────────────────────
DEF.two-carriers-for-a-role: a methodology role is carried EITHER as a standalone specialist (a Code agent or a Science profile) OR as a piece of inline guidance (a skill). The two are not interchangeable, + which form a role takes is a deliberate choice.
RULE.standalone-earned: the heavier standalone form has to be EARNED — a role earns it only when it shows a real signal that delegation buys something: its exploration would clutter the main thread + only a distilled summary should return, OR it should run on a different model, OR it needs a different toolset than its caller, OR it is a fresh-eyes pass over work someone else already produced. Absent every one of those signals, the role is SKILL-shaped, because delegating a decision you must then act on yourself is pure round-trip overhead: you would ask an isolated subagent, wait for a summary, + act inline anyway.
EX.stats-advisor: the statistics method-advisor is the worked case — it has NONE of those signals. It is guidance you consume + act on in your own context as you work, so on Claude Code it is a skill that loads inline. Claude Science has no inline-advisor-skill mechanism at all, so the same content rides a profile there instead. That is the same discipline in the lightest carrier each platform can offer, not a one-to-one gap to be closed.
RULE.lightest-form: pick the lightest form that captures a real signal, + treat a role that takes different forms on the two sides as a carrier choice, never as a defect.

# ─── §6 KEEPING THE TWIN HONEST ────────────────────────────────────────────
WHY.machinery-not-discipline: two mechanisms hold the twin coherent, + both replace discipline with MACHINERY, for the same reason: discipline leans on memory + attention, the two things code does not have + a working agent cannot rely on in itself.
MECH.gate: the first mechanism is the GATE. Coherence is enforced structurally rather than by good intentions. You edit the SOURCE, never the built artifact: a Science change lands in the source tree + the bundle is rebuilt from it. Fail-closed gates block at the moment of the write rather than flagging it for later. Any count or status is COMPUTED at check time rather than written down, because a number typed into prose is a claim about a file that goes stale the moment the file changes + will not update itself.
MECH.flag: the second mechanism is the FLAG. A behavior measured on one platform is FLAGGED for re-measurement on the other, never carried across as a fact. EX (message-steering): on Claude Code, a message sent to a running subagent was measured to arrive at its next tool call — that delivery timing is a Claude Code measurement. It is NOT a Claude Science fact, + the Science delivery timing stays unmeasured until someone measures it on Science. Importing the Code figure would be asserting what one system does from a measurement of a different system, exactly the move the flag exists to forbid. The async Science interface never even had the "cannot steer mid-run" limitation the Code correction was written for, so the Code figure would answer a question Science never asked.

# ─── §7 HOW THE TWIN STAYS IN SYNC ─────────────────────────────────────────
HABIT.three: coherence over time comes down to three habits, each aimed at a specific way twins rot.
HABIT.owner-and-authorities: one document is the OWNER-OF-RECORD for what the two sides share + how, + the port-direction questions route to their own named authorities.
HABIT.classify-same-session: when you add or change a load-bearing item, you classify it into a tier in the SAME session, while the platform reasoning is still fresh, because a classification deferred is a classification that later reads as an intentional exclusion — indistinguishable from something simply forgotten.
HABIT.one-owner-per-topic: you keep ONE owner per topic, because two current copies of a fact drift apart + the divergence is undetectable, which is the worst kind of poison a shared record can carry.
HABIT.route-to-owner: you route every question about what a thing is, where it lives, + why it sits there to the owner-document rather than to your own recollection, with the owner-document winning any disagreement.
FACT.historical-authority: one of the port-direction authorities — the record of Science skills deliberately not ported back — lives in a historical tree OUTSIDE this mirror + is not readable from here; where it comes up, that is exactly what to say about it.

# ─── §8 WHAT GENERALIZES ───────────────────────────────────────────────────
GEN.bidirectional: port direction is BIDIRECTIONAL. Neither platform is the privileged source. Shared content can originate on either side + flow to the other, so a port reads the origin side's own record rather than assuming a fixed direction of travel. EX: the writing-science engine began on Claude Science, was ported to Claude Code, + its later upgrades now flow BACK to the Science kernel. Assume a fixed direction + you would overwrite the newer origin with a stale copy, or re-derive something that already exists.
GEN.verify-the-gate: a gate earns trust only after it is SHOWN to catch the defect it exists to catch. You plant the exact fault the gate is meant to stop, confirm the gate fires, + only then rely on it. An untested gate is just another unverified claim, one layer down. EX: the toolkit's own build gates shipped with real bugs their fixtures caught — a checker that crashed on legitimate input, + a false pass that let an empty field through because a null value stringifies to non-empty text. Verify the verifier, then let it speak.
GEN.reaches-past: what reaches past this particular toolkit? The GENERATIVE FACT is specific — this twin exists because Claude Code is a local process + Claude Science is a remote sandbox. But the SHAPE around that fact is general: any system that carries one body of content across two platforms with disjoint mechanisms meets the same three-way split into a portable core, a re-expressed middle, + platform-only pieces. The ban on pasting a mechanism across the divide, the reading of an absence as a question, + the need to enforce coherence in code rather than memory all carry over with it. A cross-platform application sharing a domain core across two operating systems is the same problem in a different dress.
GEN.two-limits: the shape has two honest LIMITS. (1) where the two targets actually share one runtime, a single artifact suffices + no split is warranted. (2) where one side is a designated upstream, direction is privileged + the bidirectional rule narrows to a one-way flow. THIS twin is precisely the case where neither carrier is canonical, which is why its discipline has to run in both directions at once.
