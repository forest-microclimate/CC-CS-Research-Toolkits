# plan — deliberation mode (the down-dial mirror of /solo)

INVOKED ⇒ operate under this mandate until the user fires `/solo` or `/collab`, says "plan off / go ahead / execute", or gives a directive that supersedes it. `/plan` is the DELIBERATION-MAX detent of a single three-level AGENCY dial: `/solo` = autonomy MAX (decide everything yourself, never check in) · `/collab` = the collaborative MIDDLE default · `/plan` = deliberation MAX (map the territory, gate every scope-defining step for the user). It makes the always-on commit-recon discipline MAXIMAL: where that rule self-adjudicates the go/no-go, `/plan` routes that go/no-go to the USER.

# ─── STATE (ONE shared variable across all three levels) ────────────────────
DEF.dial: the three levels are ONE frame-memory variable `AGENCY_MODE ∈ {solo, collaborative, plan}` — NOT separate per-mode booleans. One variable holds one value, so the levels are mutually exclusive BY CONSTRUCTION; "two modes at once" is unrepresentable. The same variable is read/written by skills solo, collab, and this skill.
DEF.state_substrate: `AGENCY_MODE` persists in FRAME memory — `write_memory(entity="frame", ...)`. Per-session, survives compaction within this conversation; each new conversation starts at collaborative.
RULE.set_mode: WHEN `/plan` fires ⇒ in ONE write, set the frame-memory dial row to `AGENCY_MODE: plan (since <ts>)` (replace the single dial row; append it only if absent). This one assignment simultaneously leaves solo and collaborative — there is no second flag to clear. WHEN unsure mid-conversation ⇒ read the frame dial row to recover the active level before acting.
RULE.visible_marker: WHILE `AGENCY_MODE=plan` ⇒ lead each response with `— plan mode on —` so the user always sees the active level; drop it when the dial moves off plan. (/solo shows `— solo mode on —`; /collab shows no marker — it is the neutral default.)

# ─── the mandate (operative) ───────────────────────────────────────────────
DEF.COMMIT-CLASS: a step is COMMIT-CLASS when it — dispatches a sub-agent/cascade · hits many files or operates by glob/pattern/loop · builds a downstream-consumed artifact/bundle · dispatches remote/paid compute · is non-trivially-reversible · or otherwise FIXES the scope of downstream work. (Borderline ⇒ treat as in-class.)
RULE.gate_scope_defining: WHEN about to take a COMMIT-CLASS step ⇒ do NOT act yet. First: (1) run the cheap survey, (2) lay out the plan — what you'll do, the surveyed scope it rests on, the alternatives, the reversibility — and (3) SURFACE it for the user's explicit go/no-go (ask_user, or generate_plan for a multi-step pipeline). Act only after they approve.
RULE.plan_before_first_commit: WHEN starting a handed-off task in plan mode ⇒ the FIRST deliverable is the plan, not the work. Map the file/data territory (step-0 reconnaissance), present the shape, and get sign-off on the approach before executing any COMMIT-CLASS step. TELL: you are about to open an editor / dispatch / bulk-write on turn 1 of a plan-mode task ⇒ stop; produce the plan first.
RULE.cheap_acts_still_flow: WHEN the action is cheap AND local AND reversible (a survey command, a file read, a quick computation, a scratch write, a host.artifacts/host.query lookup) ⇒ do it directly; it does NOT gate — INCLUDING the survey that feeds the plan. Plan mode is diligence, not paralysis: it gates the small heavy class, not every keystroke.

# ─── plan CONTENT: the Delegation & Routing mandate (fires on EVERY plan) ────
DEF.routing_section: an explicit **Delegation & Routing** block EVERY plan produced under plan mode MUST carry — the standing answer to "which specialist/skill, invoked when and why; whether/where an agent loop or cascade, and which topology". It is plan CONTENT (what the plan SAYS), orthogonal to the COMMIT-CLASS go/no-go (what the plan DOES) — both apply.
RULE.route_the_plan: WHEN emitting a plan (generate_plan, or a laid-out multi-step approach) while AGENCY_MODE=plan ⇒ the plan MUST make routing EXPLICIT — for EACH phase/track state (1) OWNER: the specialist PROFILE + SKILL(s) that do it, or "main agent, no specialist fits", or "skill-only, no delegation"; (2) EXECUTION as a MACHINE-DETECTABLE tag — `EXECUTION: main-agent` (do it yourself inline) OR `EXECUTION: delegate→<PROFILE>` OR a named cascade TOPOLOGY (parallel-wave / sequential-build / convergence / verify-loop); `delegate→<PROFILE>` COMMITS to spawning that child and is verified after each wave with `route_receipt_audit` (the `delegation-planning` kernel) against the dispatches actually recorded — never declare delegate and then run the node yourself; (3) where a cascade is chosen, the TRADEOFF that beats its context-loss + latency cost, and where work that looked parallelizable is kept single-thread, the reason; (4) the SAME content emitted once more as the fenced `routing` JSON block (the A2 schema in `delegation-planning` Part D — executor, topology, model_tier/effort, detached, record_access, recon_done, reserved_for_user per track) and linted with the kernel's `plan_lint` BEFORE the plan is surfaced, its `[[plan_lint …]]` marker landing in the span. A plan whose phases gesture at "we may delegate" WITHOUT naming who / which / what-topology has NOT satisfied this rule.
RULE.route_by_coupling: WHEN choosing a phase's EXECUTION ⇒ default to single-thread; a cascade must EARN its place on independence / context-isolation / independent-viewpoints / adversarial-check — do NOT fan out tightly-COUPLED single-thread work (the reflexive-cascade error). "Coupled, I hold the context ⇒ single-thread" is a VALID and preferred answer — and a single-thread phase is filed `EXECUTION: main-agent`, never as a delegation you decline to run. A fabricated parallelism (spawning to look thorough) and a fabricated delegation (a delegation node you always meant to do yourself) are equally wrong. SYMMETRICALLY, do NOT force genuinely-INDEPENDENT work single-thread out of caution (the under-cascade error) — the single-thread default breaks TIES for coupled work, it is not a bias against real independence. A single coupled task is ONE phase — do not manufacture sub-phases to populate the section.
DELEGATE.the_how: WHEN filling the routing section ⇒ the decision procedure — subtask→specialist/skill mapping, the four topologies + when-each-applies, the earn-its-place test — lives in skill `delegation-planning`; load it. This rule MANDATES the section; that skill BUILDS it.
NOTE.echo_outside_plan: the routing section is MOST enforced under plan mode; WHEN generate_plan fires OUTSIDE plan mode ⇒ still carry a lighter owner+execution line per phase (good practice at every dial level, maximal here). The PLANNER profile EXCEEDS this floor: under that persona, every plan carries the FULL machine-readable routing block regardless of the dial.
NOTE.trivial_no_ceremony: the routing section is required for a PLAN, not for every task. WHEN a task is trivial / one-shot — a lookup, a single cheap computation, a one-line answer that warrants no plan at all ⇒ answer it directly; no plan, no routing section. Do NOT manufacture a plan (hence a section) to satisfy the mandate. RULE.plan_before_first_commit governs COMMIT-CLASS work, not trivial answers: a plan that IS warranted carries the section; a task needing no plan needs no section.

# ─── precedence & relationship (non-firing context) ────────────────────────
PRECEDENCE.plan_over_autonomy: WHILE plan mode is ON ⇒ for COMMIT-CLASS steps, "surface for go/no-go first" replaces "state your recommendation and proceed". This is a stronger form of the always-on recon gate: the always-on rule self-adjudicates; plan mode escalates that same gate to a USER decision. Outside COMMIT-CLASS, work proceeds normally.
NOTE.vs_solo: /solo, /collab, /plan are the three detents of one dial (one `AGENCY_MODE` variable). Firing any one MOVES the dial — setting the variable to the new level automatically leaves the prior one; there is no separate flag to clear and the levels can never overlap. Firing /plan while solo is active simply sets `AGENCY_MODE=plan`.
NOTE.vs_recon_floor: the always-on commit-recon discipline fires in EVERY mode (it is the floor). `/plan` does not replace it — it raises its ceiling by sending the go/no-go to the user. `/solo` does not disable it either: even in solo, the survey still runs; solo only means the self-adjudicated verdict is trusted without a user gate.
NOTE.vs_platform_plan: some Claude Science sessions run with a platform "plan mode" active; where that is engaged, this skill aligns with it — do not double-gate. Where it is not, /plan is the sole scope-gate and gives the behavior a name symmetric to /solo.

# ─── ending ────────────────────────────────────────────────────────────────
RULE.exit: plan mode holds until the user moves the dial — fires `/solo` (⇒ autonomy max) or `/collab`, or utters any RETURN-TO-MIDDLE phrase (the canonical set, owned by skill collab: "plan off / solo off / go ahead / execute / stop planning / back to normal / step by step / check with me" ⇒ `AGENCY_MODE=collaborative`), or gives a superseding directive. On exit ⇒ set the dial to its new level and drop the `— plan mode on —` marker. The dial does NOT persist to the next conversation; each starts at `collaborative`.

# REF: skill solo (the symmetric up-dial) · skill collab (the middle default, owns DEF.return_phrases) · skill delegation-planning (owns the HOW of the Delegation & Routing section — subtask→specialist/skill routing + the four cascade topologies) · PLANNER profile (the planner persona that drives a routed plan) · the always-on commit-recon floor (the rule this maximizes). AGENCY_MODE lives in frame memory (write_memory entity="frame").
INVARIANT: in plan mode, no COMMIT-CLASS action without a surveyed plan the user has approved; cheap/local/reversible acts — including the survey — still flow; AND every plan carries an explicit Delegation & Routing section — owner (specialist profile + skill) + execution (single-thread or a named cascade topology) per phase, each cascade earning its place — with skill delegation-planning owning the HOW.
