## 04 · CORE AGENTIC WORKFLOWS
- FOR: the repeatable loops Anthropic's internal teams use to get production work out of Claude Code — pick one by the SHAPE of the task.
- HANDLE: an autonomous coworker who "reads your files, runs commands, makes changes, and works through problems while you watch, redirect, or step away entirely" — these workflows are how you brief and how you VERIFY that coworker ([Best practices](https://code.claude.com/docs/en/best-practices)).
- SPINE — **give Claude a check it can run.** "Claude stops when the work looks done"; with no verifiable check, YOU are the verification loop and "every mistake waits for you to notice it." Give it a pass/fail signal — a test suite, a build exit code, a linter, a script that diffs output against a fixture, a browser screenshot — and "the loop closes on its own" ([Best practices](https://code.claude.com/docs/en/best-practices)). Gate strength scales: in-one-prompt → a `/goal` condition re-checked every turn → a `Stop` hook that blocks the turn until the check passes → a second-opinion subagent. Every workflow below is a way to MANUFACTURE that check.
- **Explore → plan → code → commit.** Separate research from execution so Claude doesn't "solve the wrong problem." (1) EXPLORE in plan mode — read files + answer questions, make NO changes; (2) PLAN — "create a detailed implementation plan" (`Ctrl+G` opens it in your editor to edit before Claude proceeds); (3) IMPLEMENT — leave plan mode, code against the plan, run the tests; (4) COMMIT — descriptive message + PR. WHEN: the approach is uncertain, the change spans multiple files, or the code is unfamiliar; SKIP the plan when "you could describe the diff in one sentence" ([Best practices](https://code.claude.com/docs/en/best-practices)).
- **Test-first (TDD).** Write tests → confirm they FAIL → write code until they pass → commit. Ideal for agents precisely because the target is machine-verifiable — it hands Claude the pass/fail check the spine demands, so it can iterate unattended until green. Composes with multi-Claude: "have one Claude write tests, then another write code to pass them" ([Best practices](https://code.claude.com/docs/en/best-practices)).
- **Iterate against an image (visual).** Give Claude a mock or screenshot and let it converge on the picture: "[paste screenshot] implement this design. take a screenshot of the result and compare it to the original. list differences and fix them" ([Best practices](https://code.claude.com/docs/en/best-practices)). WHEN: UI work — here the IMAGE is the verifiable check, and the browser screenshot is the read-back.
- **Split writer from reviewer (multi-Claude).** Have a SECOND, fresh instance review the first's output: "a fresh context improves code review since Claude won't be biased toward code it just wrote" ([Best practices](https://code.claude.com/docs/en/best-practices)). Writer/Reviewer pattern — Session A implements, Session B critiques `@file` for edge cases + races, A addresses. The adversarial-review variant runs the reviewer as a subagent that "sees only the diff and the criteria you give it, not the reasoning that produced the change," so "the agent doing the work isn't the one grading it" — tell it to flag ONLY correctness/requirement gaps, else a gap-seeking reviewer drives over-engineering.
- **Parallelize on worktrees.** Run separate CLI sessions in ISOLATED git checkouts "so edits don't collide" ([Best practices](https://code.claude.com/docs/en/best-practices)) ⇒ N independent workstreams advance at once without stepping on each other's files (compose with subagents [03_agents] + harnesses [07_dynamic_workflows]; the desktop app manages each in its own worktree visually).
- **Go headless for CI + fan-out (`claude -p`).** `claude -p "prompt"` runs non-interactively — the entry point for CI pipelines, pre-commit hooks, and scripts; `--output-format json|stream-json --verbose` for programmatic parsing. FAN-OUT batch: have Claude list the N target files, then loop `claude -p "migrate $file … return OK or FAIL" --allowedTools "Edit,Bash(git commit *)"` — pilot on 2–3 files, refine the prompt on what breaks, THEN run at scale; `--allowedTools` scopes what an unattended run may do ([Best practices](https://code.claude.com/docs/en/best-practices)).
- INVARIANT: each workflow's power IS the verifiable check it creates — a failing test, a target screenshot, a fresh-context reviewer, a batch OK/FAIL ⇒ if a task has no check Claude can read, MANUFACTURE one before automating it, else "looks done" is the only signal available and you never get to walk away.
- FEEDS: plan mode + `/goal` + `Stop` hooks (02_skills_and_commands catalog / 01_extension_architecture hooks / 06_loops) are the gates; multi-Claude + worktrees + fan-out scale into subagents (03_agents) and dynamic-workflow harnesses (07_dynamic_workflows); headless `claude -p` underpins loops + schedules (06_loops).
