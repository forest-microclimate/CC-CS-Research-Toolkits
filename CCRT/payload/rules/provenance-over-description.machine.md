# RULE: WHEN asked — or about to assert / decide / DISPOSITION — what an evolved system currently IS or DOES ⇒ answer from the PRIMARY RECORD of what it PRODUCED (lineage · build graph · VCS blame · the shipped artifact's own reproduction code · running the entrypoint), NEVER from a source that only DESCRIBES it (docstring · README · memory row · standing-context prose · a prior handoff). Agreement among descriptive sources is ZERO additional evidence until at least one is confirmed to be the primary record — non-independent sources echo, they do not corroborate. And the ABSENCE of a description is not evidence about the record: a "not found / cannot verify / defer" about a source-claim is earned only after the primary record itself was reached on its path (RULE.proof_of_reach).
# ORIGIN: 2026-07-16 post-mortem FM-001 (a tall-forest flux-tower gap-fill pipeline; project id + root frame id elided as <lineage id>). The agent asserted the shipped scalar engine was "a SINGLE GLOBAL smoother (seam=0 by construction)" — read from a SUPERSEDED engine script's docstring, reinforced by 5 un-retracted memory rows and one ambiguous standing-context line: three NON-INDEPENDENT echoes of one stale belief. The shipped product's own lineage (the shipped composite engine, version <lineage id>) shows a chunked / cosine-tail-spliced / AR(1)-bridge composite in which the global smoother survives only as Stage-1 diel priors. User caught it: "I thought we did a LOT of work to NOT use the global smoother, and make it chunked Bayesian?" The distinguishing check — one live host.lineage read — was available and skipped.
# SELF-DEMO: this rule was authored only AFTER re-deriving the toolkit's real state from its primary record (the payload tree + MANIFEST.tsv), which caught 5 claims in a 1-day-old handoff that had already drifted off the record (see CASE.handoff-drift). The rule dogfoods itself: its own origin story is a provenance check that paid off.

# ─── DEF (non-firing premises) ─────────────────────────────────────────────
DEF.primary-record: the record of what a system actually PRODUCED — read from the thing itself, not from a claim about it. Substrates: an artifact's reproduction lineage (host.lineage[vid]["code"]); a build graph / Makefile / dependency DAG; VCS blame on the behaviour; the shipped artifact's own bytes; running the entrypoint and reading what it does. The primary record is downstream of the actual behaviour, so it cannot be stale-relative-to-behaviour the way a description can.
DEF.description: any source that TALKS ABOUT what a system does rather than BEING what it did — a module/function docstring, a README, a durable-memory row, injected standing-context prose, a prior session's handoff/brief, a comment. Descriptions are claims; they are authored once and drift as the system evolves past them. A description is evidence of what SOMEONE BELIEVED at authoring time, not evidence of current behaviour.
DEF.evolved-system: any system that (a) changes its methods/config/architecture over time, (b) keeps superseded artifacts for auditability, and (c) records state in durable memory and/or standing context. This is the normal shape of a multi-session research pipeline or a maintained toolkit — NOT an edge case. All three properties are things teams rightly want; the failure is their good side-effects left un-maintained.
WHY.descriptions-drift: a description is written to match the system AT ONE MOMENT and is not automatically re-written when the system moves on. The gap between "what the docstring says" and "what the code does" opens silently and widens monotonically. The primary record has no such gap because it IS the behaviour's own trace. So on any "what does it do NOW" question, the description is the higher-variance source and the record is the lower-variance one — and the record is usually one call away.

# ─── THE CORE RULE (5 atoms) ───────────────────────────────────────────────
RULE.answer_from_provenance: WHEN the question or your next assertion is about what an DEF.evolved-system currently IS / DOES / USES / SHIPS ⇒ resolve it against the DEF.primary-record BEFORE asserting. A DEF.description may POINT you at what to check; it may NOT be the answer. TELL: you are about to state a method-of-record / architecture / version / config / "canonical" / "latest" fact, and the source in hand is a DEF.description ⇒ STOP; go read the record (PROC.provenance_check). The one exception: the description IS the deliverable under review (you are editing the docstring itself) — then you are working ON the description, not FROM it.
RULE.non_independent_agreement_is_zero_evidence: agreement among sources corroborates ONLY when the sources are INDEPENDENT (three instruments reading one temperature). WHEN several sources agree but all are DEF.descriptions downstream of one origin (a docstring, the memory rows copied from it, the context line summarizing it) ⇒ their agreement is ZERO additional evidence — one belief echoed N times, not N confirmations. TELL: you feel more confident because "multiple sources say X" ⇒ check the PROVENANCE / INDEPENDENCE of the agreeing sources, not their COUNT; if you cannot name one that is the primary record, you have zero.
RULE.selection_is_not_architecture: a method-SELECTION fact ("we chose a global smoother over a chunked Bayesian fit"; "we picked library X") is a DIFFERENT KIND of fact from an architecture-OF-RECORD fact ("the shipped engine IS a single global smoother"). Do not answer an architecture question with a selection fact. This mis-fires HARDEST when the selected component also appears INSIDE the architecture (the global smoother survives as the composite's Stage-1 priors), so the selection statement is never cleanly false — partial truth is what makes it sticky. TELL: a "we chose/abandoned/use X" statement is being used to answer "what is the shipped structure" ⇒ they are two fact types; go to the record for the structure.
RULE.supersede_with_retract: WHEN a design supersedes a prior one ⇒ RETRACT the stale DEF.descriptions (files, memory rows, context wording) at the moment of supersession — do NOT only append the new fact. An un-retracted description is the seed of the next phantom consensus. This is the READ-side rule's obligation on the WRITE side; the mechanics (3-layer in-band neutralization, tombstone superseded files) are owned by doc-currency.machine.md RULE.currency — REF it, do not duplicate. TELL: you are saving a new fact that makes an older description false and leaving the old one live ⇒ incomplete supersession; you owe the retraction in the same change.
RULE.proof_of_reach (the DECLINE-side mirror): the four rules above guard against asserting a POSITIVE claim from a DEF.description. This one guards the NEGATIVE disposition — "not found" / "cannot verify" / "defer for lack of evidence" / "unverifiable". Such a disposition is a claim about the DEF.primary-record ("the record does not settle this"), so it is earned ONLY after the primary record itself was reached on its path — NOT after only a DEF.description of it (a summary memo, an index row, a loaded context blurb, a prior note) came up empty. The absence of a description is evidence about the description layer, NOT about the record: a missing assessment-memo says nothing about whether the source PDF confirms the claim. Valid pass = PROOF-OF-REACH, not a ban on reporting absence: "I opened the primary record on its path and it is genuinely silent / absent" is a sound disposition; "no memo/index-hit exists, so I cannot verify" is not. This rule fires on APPLY, DEFER, and REJECT alike — any disposition of a source-claim, not just the loud give-ups (the quiet reasoned defer is the dangerous case: it reads as discipline). TELL below = TELL.absence_for_record. NOTE: a description may still POINT (an index says "the PDF is at path P" ⇒ go read P); it may not be the terminal answer that P's content is unconfirmable.

# ─── TELLS (output-detectable; ordered most→least specific — any one fires ⇒ PROC.provenance_check) ───
# TELLS 1–6 gate a POSITIVE assertion from a description; TELL 7 (absence_for_record) gates a NEGATIVE disposition (not-found/cannot-verify/defer) taken from a MISSING description. Both resolve to the same PROC (reach the primary record before you commit).
TELL.provenance_source_mismatch: about to assert what a system currently does/uses FROM a DEF.description rather than the DEF.primary-record. THE core signal; the rest are its symptoms.
TELL.non_independent_agreement: several secondary sources agree, none is the primary source, and you are treating the agreement as confirmation (RULE.non_independent_agreement_is_zero_evidence).
TELL.recency_overwrite: a newly-read source FLIPS a belief you stated CORRECTLY earlier in the SAME session. A flip ⇒ reconcile both framings against the record; do NOT silently adopt the more recent one. (FM-001: an early message stated the architecture correctly → a later message flipped-wrong after reading the docstring.)
TELL.selection_answering_architecture: a method-SELECTION fact is being used to answer an architecture-OF-RECORD question (RULE.selection_is_not_architecture).
TELL.part_for_whole_collapse: reducing a multi-component spec to ONE component's headline (FM-001: object 1 of 4 → "the whole engine"). Confirm the headline describes the WHOLE, not a stage.
TELL.name_resolved_provenance: an artifact was identified by NAME-MATCHING an overloaded token (one word that names a quality-tier, a file, AND a data-prefix at once) rather than by lineage; and/or a DECLARED input edge the code never reads is being treated as a functional dependency.
TELL.absence_for_record (the decline-side tell — RULE.proof_of_reach): about to emit "not found" / "cannot verify" / "defer for lack of evidence" / "unverifiable" about a source-claim, having reached only a DEF.description (a memo/index/context-blurb/memory came up empty) and NOT the DEF.primary-record itself on its path. The give-up is being justified by a MISSING description. Distinctive shape: the disposition reads as disciplined caution ("I won't inject an unverified claim") while the reachable primary record was never opened — so the tell is NOT give-up-language (that misses the quiet reasoned defer); it is the absence of a shown primary-record read before ANY disposition (APPLY/DEFER/REJECT) of a source-claim. Fires ⇒ PROC.provenance_check step (2) on the DECLINE path: name the primary record, reach it on its path, and only then dispose. This tell is also the seed line for a verification/auditor pass (see NOTE.auditor-seed): a cold auditor SEES the unopened-record fact but, unseeded, adopts the agent's "disciplined defer" framing and blesses it — seeded with this tell, it reclassifies the same fact as a blocking omission.

# ─── PROC (the cheap check the rule mandates) ──────────────────────────────
PROC.provenance_check (run the moment a TELL fires, BEFORE asserting): (1) NAME the claim as a testable proposition ("the shipped X uses architecture A"). (2) IDENTIFY the primary-record substrate available here — pick the FIRST that exists: shipped-artifact lineage/reproduction code · build graph · VCS blame · run the entrypoint. For a source-claim about a document (TELL.absence_for_record), the primary record is the SOURCE ITSELF on its path (the PDF/file/dataset), not a memo/index about it. (3) READ it and re-derive the fact from the record. (4a) POSITIVE path: if record and description AGREE ⇒ assert, now grounded. If they DISAGREE ⇒ the record wins; and you have found a stale description ⇒ trigger RULE.supersede_with_retract on it. (4b) DECLINE path (TELL.absence_for_record): after reaching the primary record — if it CONFIRMS the claim ⇒ APPLY (the defer would have been wrong); if it REFUTES ⇒ REJECT with the record cited; if it is GENUINELY SILENT/ABSENT on its path ⇒ NOW "cannot verify / defer" is earned, and record "checked primary record R at path P, genuinely silent" (proof-of-reach), not "no description found". The one thing that is never a valid terminal disposition: "cannot verify" justified only by a missing description. (5) COST NOTE: step (3) is typically one call (one host.lineage read; one `git blame`; one entrypoint run; one PDF/text extract). Detection is cheap; the cost of a wrong method-of-record premise — or a verifiable fact wrongly deferred — is paid only downstream, after it has shipped into a decision — the asymmetry favours ALWAYS running the check.

# ─── PLATFORM SPLIT (non-firing context — same mechanism, different substrate) ───
NOTE.platform: the rule is substrate-agnostic; the primary-record SUBSTRATE differs by platform.
  | role                | Claude Science                              | Claude Code                                   |
  |---------------------|---------------------------------------------|-----------------------------------------------|
  | description source  | *_engine.R docstring; injected project ctx  | README / module docstring; CLAUDE.md          |
  | un-retracted trail  | append-mostly durable memory rows           | CLAUDE.md accreting "we use X" notes           |
  | PRIMARY RECORD (gate)| host.lineage[shipped]["code"]              | run the entrypoint · read the build graph · git blame the behaviour |
  | supersession residue| a live superseded engine file               | a refactored-out module left in the repo      |
NOTE.registry-instantiation: where a class of these questions recurs, PIN the answer in a machine-readable registry keyed to the SHIPPED-PRODUCT lineage (not to any docstring) + a fail-closed self-check that re-derives from the record and refuses to agree if they diverge. Reference instantiation: a canonical-methods skill + its verify function (fail-closed; re-derives the method-of-record from the shipped lineage). The toolkit's coupling-manifest + its verify gate is the SAME pattern for a different class (agent↔skill couplings): authoritative record + fail-closed gate.
NOTE.auditor-seed (the CATCH complement to the always-on rule — where a hard gate is unavailable, e.g. no turn-end hook): TELL.absence_for_record is written to be inheritable by a fresh-context verification/auditor pass as a single checklist line: "PROOF-OF-REACH — for every disposition of a source-claim (applied/deferred/rejected), the reasoning must show the PRIMARY RECORD was reached on its path, not merely a description of it; a 'cannot verify / not found / defer' whose primary record was reachable and unopened is UNSOUND — absence of a secondary summary is NOT primary unavailability." WHY it must be SEEDED, not assumed: a cold auditor SEES the unopened-record fact but, un-seeded, adopts the traced agent's own "disciplined defer" framing and blesses the omission; seeded with this line it reclassifies the same fact as a blocking omission. EVIDENCE (2026-07-17 replay of CASE.izuno-defer, incidental elicitation, 2 arms n=4): unseeded auditor 0/4 caught the omission (4/4 surfaced the unopened PDF yet all 4 called the deferral "sound"); seeded 4/4 caught it "blocking". This is why proof-of-reach lands inside a cold auditor's competence: it is a PROCESS tell (was a primary-record read issued before this disposition?), not a substance judgment about the source's content — so it works for an OMISSION the way tells 1–6 work for a false commission, without the auditor needing to understand the domain.

# ─── CASES ─────────────────────────────────────────────────────────────────
CASE.single-global-smoother (FM-001, the origin): four shipped scalar composites produced by the shipped composite engine (chunked-overlap-block + cosine-tail-splice + OU/AR1-bridge composite; visible in the record as block-length / overlap-window / fine-cap constants, a cosine-taper weight, and an AR(1)-bridge term). The agent collapsed the whole to "single global smoother" by reading a superseded engine script's docstring — a superseded engine whose architecture appears in ZERO shipped products. Every TELL above fired at once; none was checked. Fix shipped: registry pinned to lineage + a fail-closed verify self-check + the superseded engine script tombstoned.
CASE.handoff-drift (this session, 2026-07-17): a 1-day-old handoff (HANDOFF_install-time-selection.machine.md) asserted the CC toolkit "has NO machine-readable manifest", "install.sh copy_tree at :122/:150", "18 agents / 41 skills", "3 pre-copy gates incl. a cross-bundle sync check", "one code-coupled pair already gated". Reading the primary record (payload tree + install.sh + MANIFEST.tsv) showed: a MANIFEST.tsv already exists (104 rows, provenance kind); copy_tree at :117/:145; 17 agents / 42 skills; only 2 gates run; that cross-bundle sync-check pair does NOT exist on the CC side (it describes the Science bundle). 5 descriptive claims drifted in ONE day. The rule caught them because the record was read before the plan was written.
CASE.izuno-defer (the DECLINE-side origin, RULE.proof_of_reach): during a manuscript QC reconcile, a framing reviewer proposed a competitor contrast — "confirm the cited paper reported communities as NESTED SUBSETS before citing." To verify, the agent read a loaded literature-review DESCRIPTION (which summarized the paper only as "richness declines, pooled, height-only" — silent on nestedness), then searched the working folder for an assessment-MEMO of that paper like the ones it had used for sibling claims; found none; and DEFERRED the finding to the open-issues register as "a source I cannot verify," reasoning it would not inject an unverified contrast. The source PDF was on a granted library path the whole time and was never opened. The agent's own post-mortem: "I treated the absence of a secondary summary as if the primary source were unavailable — exactly backwards." Two descriptions came up empty (lit-review blurb, missing memo) and their absence was read as record-silence; the give-up read as discipline, which is why no positive-side tell fired. Sibling failure same session: a paper WAS in the PDF folder but reported "not found" because the INDEX (a description of the folder) mis-recorded it — folder-is-record, index-is-proxy. Fix shipped: RULE.proof_of_reach + TELL.absence_for_record + NOTE.auditor-seed (replay-validated: seeded auditor 4/4 catch vs unseeded 0/4).

INVARIANT: on any "what does it do NOW" question about an evolved system, the primary record outranks every description of it, and descriptive agreement counts for nothing until one source is confirmed to be the record — and symmetrically, the ABSENCE of a description outranks nothing: "cannot verify / not found / defer" is earned only by reaching the primary record on its path, never by a missing memo, index, or note. Present-description, agreeing-descriptions, and absent-description are the same error in three poses: the record is the answer; the description is never the terminal word, whether it speaks, echoes, or stays silent.
