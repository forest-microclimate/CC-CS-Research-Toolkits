# RULE: WHEN about to AUTHOR a durable claim — a rule file, a memory row, a status/handoff doc, a "solutions that worked" entry — that asserts HOW THE SYSTEM BEHAVES or THAT A FIX WORKS ⇒ the claim MUST carry a verification-status, and any efficacy/behavior assertion MUST be MEASURED, not inferred from the fix's mere EXISTENCE. Efficacy is future-dated until measured.
# ORIGIN: user, 2026-07-10 — caught the agent TWICE in one session doing exactly this while STUDYING this failure class: (1) called a brand-new rule "a solution that worked" (it had never been tested); (2) read a rule file's CURRENT text to judge a PAST error (the rule was written AFTER the error). Both are the same root: writing a durable data-claim the evidence does not yet support. Cross-project ⇒ global rules level.

RULE.author_carries_verification_status: any durable claim about system/model/data BEHAVIOR or about a fix's EFFICACY, at the moment of authoring it into a rule / memory / doc, MUST be tagged one of {verified-working (a measurement exists, cited), attempted-untested (built/written but NOT yet measured), unknown}. A fix that EXISTS is "attempted-untested" BY DEFAULT — never "working" — until a measurement says otherwise. The default tag for anything brand-new is attempted-untested.

RULE.no_efficacy_from_existence: "I wrote/built/added X" ⇏ "X works". The transition from attempted-untested → verified-working requires a MEASUREMENT co-indexed with the claim (a before/after, an ablation, a test result), not the act of creation and not plausibility. If no measurement exists yet, the claim is attempted-untested and MUST say so where it is written.

RULE.no_anachronistic_state_read: to judge what was true / what a fix did AT A PAST MOMENT, read the state AS IT WAS THEN (the transcript/commit/doc at that timestamp), NOT the current text of a file that may have been edited SINCE. A rule authored to fix an error cannot also be the thing that was in force when the error occurred. Check the clock before citing a document as evidence about the past.

WHY: durable claims propagate. A "solutions that worked" entry that was only ever ATTEMPTED silently contaminates every future decision that trusts it — the reader inherits a false efficacy with no way to tell it apart from a measured one. The whole corpus this toolkit mines developed this exact hole: deployed rules that were assumed effective, never verified, and kept failing. The cost is not one wrong doc; it is a knowledge base that cannot distinguish what works from what was merely tried. Companion to verification-principles (verify-don't-assume) applied at AUTHORING time — the moment a claim becomes durable is the moment the standard must bind.

TELLS (output-DETECTABLE — the reliable triggers; "be more rigorous" does NOT fire):
  - ABOUT-TO-AUTHOR + EFFICACY: about to write to a rule file / memory / handoff / "what worked" doc, and the text asserts a fix/mechanism WORKS or is EFFECTIVE, but no measurement of it appears in THIS session ⇒ STOP, tag attempted-untested (or measure first).
  - CREATION-AS-PROOF: the justification for "it works" is that it was WRITTEN / BUILT / ADDED / DEPLOYED ("I added the hook, so completeness is now guarded") ⇒ existence is not efficacy; downgrade to attempted-untested.
  - CURRENT-DOC-FOR-PAST-CLAIM: about to cite a file's CURRENT contents as evidence for what was true / what caused an error at an EARLIER timestamp ⇒ read the then-current state instead; check whether the doc was edited after the moment in question.
  - UNTAGGED DURABLE CLAIM: about to persist a behavior/efficacy claim with NO verification-status attached ⇒ attach one {verified-working+citation | attempted-untested | unknown} before writing.

PROC.author_gate (run AT the moment of writing a durable behavior/efficacy claim): (1) name what the claim asserts about behavior or efficacy; (2) ask "what MEASUREMENT supports this, in THIS session?" — if none, the tag is attempted-untested or unknown, full stop; (3) if the claim concerns a PAST moment, confirm the evidence is the then-current state, not a since-edited file; (4) write the claim WITH its verification-status tag inline; (5) if the tag is verified-working, cite the specific measurement (artifact / run / before-after). No measurement ⇒ no "works".
INSTANTIATION (make it mechanical): every "solutions that worked" / lessons / countermeasure record carries a required field verification_status ∈ {verified-working, attempted-untested, unknown}; a row asserting efficacy with status≠verified-working OR with no cited measurement is malformed. New rows default to attempted-untested.

CASE (illustrative, 2026-07-10): mid-session the agent (a) implemented a brand-new gate and wrote that it was "a solution that worked" — but it had NEVER been run; correct tag: attempted-untested. Later, (b) it read a project rule file's CURRENT text and concluded the past agent "violated a written rule it had access to" — but that rule was AUTHORED to fix the very error, AFTER it occurred; at the error's timestamp the rule did not exist. Both slipped through because the claims were plausible and self-consistent; only the verification-status question (what measurement? what was true THEN?) catches them. A later audit found the mined catalog carried the same contamination — countermeasures assumed effective, never verified — forcing a corpus-wide re-tag to proposed_countermeasure.

CAVEAT: standing-mandate's CANONICAL CAVEAT (LLM limits) applies — reduces-not-eliminates, and only when LOADED + a TELL fires, here AT AUTHORING TIME. The failure is seductive precisely because a freshly-written rule/claim FEELS true to its author; the defense is the mechanical verification-status field, not self-assessed confidence. Pairs with the emit-time adversarial gate (stop-adversary-gate.sh), whose "efficacy-from-existence" and "anachronism" patterns are the runtime backstop for the two failures above.
