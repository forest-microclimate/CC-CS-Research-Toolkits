# directing-execution — run a plan you already designed, and adapt it as it unfolds
# WHAT: the RUN-TIME half of orchestration. delegation-planning decides the distribution BEFORE dispatch; THIS drives it AFTER — supervise each wave, read what comes back, and choose continue / re-route / fix-first / abort / goal-met / adapt-the-plan. The director DISPATCHES and re-launches; it does not PERFORM the domain steps (those route to specialists).

## When to invoke
WHEN a plan is APPROVED and now EXECUTING and you are the lead directing it — especially under `/solo` ("proceed autonomously") — with subagents launched and reports landing. Concretely: you just launched a wave and must act on the returned reports · a subagent returned garbage / off-charter output · a result changes what the next phase should be · you are tempted to spawn another cascade and must decide if it is warranted. NOT before dispatch (that is the design-time routing decision -> `delegation-planning`); NOT the persona question (-> `planner` agent).

## The signature error this prevents
**Thrash and drift under autonomy** — two run-time failures:
1. OVER-REACTION: re-routing, re-spawning cascades, or rewriting the plan on NOISE — one weak result, a partial answer — churning the orchestration without new information. Reflexive-cascade at run time.
2. UNDER-REACTION / DRIFT: mechanically running the approved plan to completion after a result has already invalidated a later phase — executing the letter of the plan past the point its purpose changed.
The fix is the same discipline as design-time: act on EVIDENCE, not on impulse or inertia — change course exactly when a result warrants it, and not otherwise.

## Load-bearing loop — supervise -> decide -> act (once per wave boundary)
Direction is BOUNDARY reactive: at each wave boundary you read what came back and choose the next action. A Task-tool subagent runs to completion and hands back ONE report, so the wave boundary is when the report(s) land. Run this loop:
1. **HARVEST** — read each subagent's returned report: its findings, the FILES it wrote (by path — subagents share the working tree), and whether it actually finished vs bailed. In Claude Code the launch returns the report directly; there is nothing async to poll.
2. **ASSESS against the plan's PURPOSE** — not just "did the subagent finish" but "did it move the plan toward its goal". A subagent can complete and still return the wrong thing.
3. **DECIDE** one of six (criteria in the next section): CONTINUE (launch the next wave as planned) · RE-ROUTE (same plan, different owner/topology for the next step) · FIX-FIRST (a defect blocks the next wave — repair it before anything else proceeds) · ABORT (stop and surface, when the goal is unreachable or a gate needs the user) · GOAL-MET (terminal — update the records, take the backup) · ADAPT (revise the plan doc — add/drop/reorder phases — then continue).
4. **ACT + RECORD** — launch / re-launch / edit-the-plan; update the task list; note *why* on any deviation so the trail explains the adaptation. Then continue to the next wave (or surface and stop).

## The six decisions — when each (the run-time WHICH)
- **CONTINUE** => results met their bar and the plan's next phase is still the right next step. Default; do NOT manufacture a course-change to look responsive.
- **RE-ROUTE** => the STEP still stands but its owner/topology was wrong (a specialist returned off-charter work, a single agent choked on what wants a fan-out, a fan-out was overkill). Change the how, keep the plan. Consult `delegation-planning` for the corrected routing.
- **FIX-FIRST** => a DEFECT the wave surfaced blocks the next one — a broken gate, a corrupted output, a wrong path baked into the remaining briefs. Repair it BEFORE anything else proceeds; a defect carried forward multiplies through every unit that consumes it. Distinct from RE-ROUTE (the routing was wrong) and from ADAPT (the plan's remaining shape is wrong) — here plan and routing both still stand, something is simply broken.
- **ABORT / SURFACE** => the goal is unreachable as framed, a hard external gate blocks (an approval, a missing credential, a GOAL-fatal data gap — one that kills the objective, NOT merely a data gap that makes one later phase pointless, which is ADAPT), or continuing would burn budget on a dead end. Under `/solo` the bar to stop is high (that is the mandate), but an unreachable goal or a genuine user-only decision still stops — `/solo` means "decide everything decidable", not "never stop".
- **GOAL-MET** => the plan's purpose is achieved and no further wave is warranted. Terminal, and it binds two acts before you stop: update the records (task list + the trail) and take the backup. Do not drift past a met goal manufacturing extra work.
- **ADAPT (revise the plan)** => a RESULT changed what the remaining plan should be — a phase is now unnecessary, a new phase is now required, an assumption broke. Edit the plan doc and keep going. This is the capability that makes direction more than a dispatcher: the plan is a living doc, not a frozen script. Adapt on a real finding, never on noise.
PERSEVERE-vs-ADAPT test: WHEN a result is disappointing but the goal is still reachable on the current plan => persevere, do not rewrite the plan — where persevere means RE-LAUNCH the failed unit with a corrected brief, patch it yourself, or re-route it to a better owner/topology (NOT churn an already-USABLE result: a mediocre-but-usable intermediate that met its bar => CONTINUE, not persevere). WHEN a result makes a later phase pointless or wrong => adapt. The difference is whether the PLAN'S REMAINING SHAPE is still correct, not whether the last result was good. Re-launch != re-route: re-launch re-runs the SAME unit (fresh subagent, corrected brief) when it failed or returned off-target; re-route changes the owner/topology when the SHAPE was wrong (e.g. a single agent choking on what wants a fan-out => re-route to a parallel-wave, do NOT grind the same brief again).

## Supervised-executor watch — the three classes (run-time; 2026-08-04)
WHEN a running wave holds a `delegate:opus5-executor` track (tier `T1_supervised`, marker `"supervised": true`) => WATCHING IT IS THE WORK, not a courtesy: `claude-opus-5` is permitted on Claude Code in exactly ONE position — a tightly-scoped supervised CHILD under your active watch — and the permission rests ENTIRELY on that watch. It is never the session default, never a coordinator or a sub-planner (it is a worker, never a router), never reached via the bare `opus`/`opusplan` aliases, and never named in a raw model field of a routing block. Watch three failure classes as OUTPUT-DETECTABLE tells in what the child says and writes — not as a feeling about how the run is going:
- **SCOPE-DRIFT (wandering)** — the child narrows, widens, or transforms the briefed task instead of naming the different reading in a sentence and continuing as asked; it reports work the brief did not ask for, or a done-condition it rewrote. TELL: its report answers a question the brief did not pose. => RE-ROUTE if the shape was wrong, else re-launch the unit with the scope restated.
- **THRASH (confusion)** — it revisits a decision it already committed to with no new information contradicting it, cycles between two approaches, or its updates re-open settled ground. TELL: the same subproblem appears in two updates with no new evidence between them. => FIX-FIRST if a defect is driving the churn; otherwise queue a steer naming the committed approach.
- **FALSE-POSITIVE OVER-CAUTION (timidity)** — it checks in on a routine judgement call, declines an action the brief authorizes, flags a non-finding as a blocker, or stops short of finishing the whole task. TELL: a stop or a question whose answer the brief already contains. => correct in the order below; do NOT read timidity as a reason to abort.
TIMIDITY CORRECTION, IN THIS ORDER (do not skip to step 2 — the usual cause is your own wording): (1) STRIP conservative language from the BRIEF first — the documented literal-compliance mechanism means a hedged brief produces a hedged run; (2) STEER the running child via SendMessage (queues, delivers at its next tool round — see the execution model below); (3) RE-BRIEF at COLLECT with the corrected wording. ## The Claude Code execution model (the constraints the loop rides on) [reference]
Claude Code subagents run via the **Task tool**. The model is deliberately simple, and the loop above is built on its limits:
- **Run-to-completion, one report** — a launched subagent executes its brief and returns a single final report; there is no async handle, no partial-result stream. HARVEST = reading that report. This is why the brief must be front-loaded: you get one shot per launch.
- **Mid-run steering via queued messages** — [SUPERSEDED 2026-07-30, MEASURED 2026-07-29] ~~No mid-run steering — you CANNOT inject a message into, or stop, a running Task-tool subagent (no Claude Code equivalent exists for mid-run steering).~~ You CAN inject a message into a running Task-tool subagent via SendMessage — it QUEUES and delivers at the child's NEXT TOOL ROUND (a live child confirmed receipt + mid-task incorporation); use it for corrections, addenda, and stop requests. A child between tool calls or already finished sees the message only on resume. A REDESIGN (a new assignment) still means LAUNCHING A FRESH ONE with a corrected brief — steering is course-correction, not design-by-drip. Prefer a tight, complete brief so steering stays rare rather than routine.
- **Shared working tree** — subagents operate in the SAME repository/working directory as you. Hand a file down by writing it to a tracked PATH the subagent's brief names; its outputs come back written to paths (and summarized in its report). There are no separate workspaces to bridge.
- **Concurrency = launch-together** — several Task-tool calls issued in ONE message run concurrently; issued across turns they run one after another. Size a concurrent wave against real headroom first (`preflight-parallel`).
- **State does not carry across launches** — a follow-up to a finished subagent is a NEW launch; it does not retain the prior subagent's context. Put whatever the follow-up needs (the prior output path, the decision so far) INTO the new brief.
- **Visibility = the returned reports** — there is no live roster or budget API; the reports you get back ARE the run state. Track which units are done, which are outstanding, and what each produced, yourself (the task list is the ledger).

## Concurrency & failure handling
- WHEN launching a fan-out wave => size it against real headroom first (`preflight-parallel`); do not oversubscribe cores/RAM on a big wave.
- WHEN a subagent returns garbage or off-schema output — EVEN WHEN it reports "done" (completion != correctness) — or bails partway => do NOT fold its output into the result as if valid. RE-LAUNCH that ONE unit (fresh subagent, corrected brief), or re-route it, or surface it — an adversarial/parse check on high-consequence output belongs here (a `verify-loop` is the topology for it; see `delegation-planning`).
- WHEN a subagent fails outright (errors out, produces nothing) => re-launch only the lost unit; the rest of the wave's reports still stand. Never fabricate a failed unit's deliverable.

## Non-goals (redirect to the named sibling)
- The BEFORE-dispatch decision — subtask->specialist/skill routing + which topology => `delegation-planning` (this skill consumes that decision and runs it).
- The planner PERSONA and the design+direction identity => the `planner` agent.
- Sizing a wave's concurrency => `preflight-parallel`.
- The autonomy MANDATE that says "keep going, decide it yourself" => the `solo` skill (this skill is the HOW of directing under it, not the dial).
- Writing a subagent's task-brief prose so it reliably complies => `eliciting-llm-behavior` + `machine-md`.
- PERFORMING any domain step (the fit, the render, the analysis) => the routed specialists. The director dispatches and re-launches; it does not do their work.
