# eliciting-llm-behavior - the "which structural lever elicits which model behavior" catalog (primary reader = the agent authoring a prompt)
# WHAT: the "which lever" catalog. Two complementary legs - machine-md = how to WRITE agent-read text (FORM); THIS = which STRUCTURAL DEVICE reliably elicits a target model BEHAVIOR (TECHNIQUE), plus how to MEASURE the lift (below). REF machine-md for FORM; do NOT restate it.
# WHY: an exhortation inside a prompt ("please output JSON", "be thorough", "don't forget X") is the WEAKEST lever - surfacing != enforcement (the same reason a bare "always do X" underperforms a trigger-bound rule). A structural device that constrains the decode space fires BY CONSTRUCTION. Measured: forcing an output schema/template fixed ~72% parse-failure; an emit-time adversarial gate cut a failure mode 100%->12%. Reach for the device, not the plea.

## TECHNIQUE TRIGGERS  (each = WHEN <the behavior you need> => DO <the lever>)
- WHEN you need PARSEABLE / fixed-shape output (named fields, a table, a verdict) => FORCE the shape with an exact output TEMPLATE the model fills in - a fenced skeleton, a labeled-field block, or a table with named columns - and instruct "emit ONLY this shape, nothing before or after". Show the empty template IN the prompt; do not merely describe the format in prose. The tighter you pin the shape, the less the decode space can drift. This is the STRONGEST lever; prefer it over every softer one below.
- WHEN the answer must be ONE OF a fixed set => pin the allowed values as an explicit CLOSED set the model must pick from - "answer EXACTLY one of: high | med | low - and nothing else" - and, on high-consequence output, add a post-check that rejects any out-of-set token. A bare prose list drifts; naming the closed set + rejecting strays is the CC substitute for an enum's by-construction guarantee.
- WHEN the task has a reliable INPUT->OUTPUT shape the model keeps missing => give 1-3 FEW-SHOT exemplars of the exact transform (show, don't tell); match the exemplar's format to the wanted output byte-for-byte (the model copies what it sees, including stray formatting).
- WHEN the task is COMPOUND / multi-step => DECOMPOSE - ordered explicit steps in one prompt, or separate chained prompts / subagent steps - rather than one leap; a model asked to do five things at once silently drops some.
- WHEN correctness needs REASONING before the answer => scaffold it: ask for the working FIRST, the answer LAST. BUT for routine extraction / classification prefer template-forcing over free chain-of-thought (cheaper, parseable, and a modern reasoning model already reasons internally).
- WHEN expertise or a viewpoint frames the task => ASSIGN the role at the TOP, in the system position - a subagent's system prompt, or the opening "You are X ..." line - not buried mid-prompt; the earliest / system position weights hardest.
- WHEN the model keeps doing an UNWANTED thing => state the fix as a POSITIVE redirect (do Y instead), not a bare prohibition - positive trigger-conditioned framing fires better than "don't", and names the wanted behavior at the moment it is due (machine-md core).
- WHEN fanning out over many items => issue ONE structured prompt PER item (same template, one item's data each), not a single prompt juggling the whole batch - a batched prompt blurs or drops items. In CC, launch these as parallel subagents (the Task tool) to run concurrently; keep one exemplar / template per call.
- WHEN a long prompt buries the ask => lead with the task in ONE line, then constraints as a scannable list, examples ADJACENT to the instruction they illustrate - primacy + recency both fire; the MIDDLE of a long prompt is where instructions get dropped.

## MEASURE  (efficacy != existence - the mandatory close)
- WHEN you claim a prompt change "works" => A/B it: run OLD vs NEW the same N times on the same inputs, count the target behavior, cite the before/after rate. Do NOT assert efficacy from the fact that you added the device. For a one-off, run each variant N times (by hand, or a small script that loops the prompt) and compare the hit rate.
- CAVEAT (LLM limits): a device RAISES P(behavior); it does not guarantee it - a template still needs valid field values, a few-shot still generalizes imperfectly. Stack a cheap verifier on high-consequence output (parse-check, assert, adversarial gate); do not trust the device alone.

# INVARIANT: reach for the structural device that constrains the output space, name the wanted behavior at the decision moment, and MEASURE the lift - never ship a prompt lever on faith.
# REF: machine-md (FORM of any agent-read text - output-detectable triggers, atom-preservation, positive framing).
