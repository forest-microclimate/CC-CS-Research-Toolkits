# supervisory-workflow

WHAT THIS IS: the load-bearing invariants of a supervised loop that runs a job larger than one agent's context. For each element: what it is, and the failure it prevents. It OMITS implementation — every mechanism is realized with whatever primitive your runtime provides. It ASSUMES you can (a) start isolated worker instances, (b) run programs, and (c) write persistent records that outlive the worker that wrote them. Where a rule depends on a further runtime property, the rule NAMES that property and tells you to measure it (see §6, §12).

VOCABULARY (one name per concept): **requester** (sets goal + boundary) · **coordinator** · **worker** · **code** · **store** · **cycle** · **brief** · **tier** · **ledger** · **receipt**.

## §1 — The problem the architecture solves
One agent instance has one bounded working context. A job whose source material + intermediate products + measurements together exceed that bound cannot be held in one instance. Attempting it produces TWO failures with one cause (no capacity remains to keep state or check claims):
1. **Loses the thread** — re-reads material already read, begins to contradict its own earlier statements.
2. **Asserts without checking** — reports a fix works, because making the claim is far cheaper than measuring it.

Decomposition into a supervised loop buys four properties, and the rest of this skill exists to pay decomposition's cost — every boundary between participants is a place information can be lost: **Isolation** (a worker holds only its own assignment; a mistake stays inside its product) · **Parallelism** (independent pieces run at once; elapsed time tracks the longest piece) · **Verifiability** (a worker's product is a named record a second party can check) · **Token economy** (each piece runs at the cheapest capability that fits; the coordinator's context stays reserved for deciding).

## §2 — Three participants and one store (they RANK EQUALLY)
**Coordinator.** Decomposes the goal, writes briefs, chooses arrangement + tier, launches, collects, verifies, synthesizes, decides the next cycle. Performs NO domain work — two reasons: its context is the only one that persists across cycles (filling it with raw source destroys the capacity the loop depends on), and a coordinator that also produces work becomes the reviewer of its own product (§8 rules that out). CARVE-OUT, deliberately narrow — the coordinator reads primary material in exactly two cases: (a) the material IS a worker's output/report, which it must read to synthesize; (b) a load-bearing claim is about to decide something consequential, or two reports disagree. Keeping the exception to two named cases is what stops it becoming the default.

**Workers.** Fresh instances, each launched with one written brief and no view of the coordinator's conversation or of each other. They do the substantive reading, writing, building, measuring. Each returns ONE bounded report and ends. Isolation is kept, not repaired: a worker that cannot see the wider conversation also cannot inherit its errors, and spends its whole context on its own assignment.

**Code.** Deterministic programs. Apply the **determinism test** to every piece of work: if it can be expressed as a fixed sequence of operations over code that exists or can be written, RUN IT AS CODE. An instance asked to imitate a program returns a slower, costlier, non-reproducible approximation. Consequence: code ranks as a product of the system alongside the other two participants, planned for and stored on the same terms. WHERE code runs is a separate question from WHETHER it should be code: inside a worker by default, directly under the coordinator only for a one-command check.

**The store.** Everything exchanged persists as a named record: briefs, outputs, reports, ledgers, measurements, and the code itself. Isolated workers have no other channel, so an unwritten result dies with the worker that held it. The store is simultaneously the communication channel and the project's history.

BOUNDARY RULE (one line): judgment is delegated, determinism is run, synthesis + decision stay with the coordinator, and anything crossing a boundary is written down.

## §3 — The cycle
One cycle = **decompose · brief · launch · collect · verify · synthesize · decide**. Everything the loop does happens inside some cycle. The DECISION is the point of the cycle: given what just came back, does the plan still fit the evidence? A plan executed to its end without re-fitting ignores everything it learned on the way. SIX exits, exactly one per cycle:
- **Continue** — plan fits, work remains → next pieces.
- **Re-route** — the evidence touched only some of the remaining pieces → re-brief ONLY those.
- **Fix-first** — a defect blocks the next cycle → repair it before anything else proceeds.
- **Abort** — work blocked or unrecoverable → stop, report the blockage to the requester.
- **Goal-met** — terminal, and it binds two acts → update the ledgers, take a backup.
- **Adapt** — the evidence moved the target; the decomposition itself is wrong → return to decompose.
Name the exit in the cycle's record: an unnamed outcome defaults silently to Continue, which is how a plan outlives the evidence that justified it.

## §4 — Arrangement (chosen per cycle by how the pieces depend, not by habit)
Five shapes: one worker alone; a **chain** where each piece consumes the last; a **fan-out** of independent pieces (a "wave"); a **convergence** — a fan-out giving several workers the SAME material and a DIFFERENT question each; a **build-then-review** pair with a separate reviewer. The last two fan-outs look IDENTICAL at launch and differ at collect: independent pieces need only collection, while several answers to different questions about one body of material need a MERGE — and that merge is coordinator work that must be budgeted before launching.

SIXTH ROUTE — **a chunk that earns its own coordinator** (weigh at every decompose). EARN TEST, all three at once: the chunk is internally multi-step and delegable, so it would need a plan of its own · it is SEPARABLE behind a narrow interface of named inputs and outputs · it is heavy enough that supervising its internals would consume the coordinator's attention at collect. Then route it WHOLE to ONE worker running the coordinator role at the TOP tier, which runs the full cycle inside it. WHY: a chunk that needs its own plan either gets one from a party that owns it, or it fragments across the coordinator's collect.
SEALED — four clauses, each closing its own failure: **narrowed scope** (read-paths = the named inputs, write-path = the subtree it owns; without it the interface stops describing what the chunk actually touches, and the separability that justified routing it whole stops being true) · **a private brief/collect area for the workers it launches**, because the shared ledgers are ONE-WRITER (the coordinator's) and two writers appending to one running record lose or interleave each other's rows · **non-overlapping write scopes where several run at once**, assigned by the coordinator, since a shared store has no lock · **a compressed ROLL-UP, not a transcript** — within its report cap it returns the outcomes it named and the receipts it checked, not its workers' reports, and the coordinator spot-checks those receipts and writes the shared ledger row itself (a transcript moves the subordinate's whole collect problem onto the coordinator, which is the cost the routing existed to avoid).
DEPTH — **ONE MEASURED level, not open recursion.** The enabling property (a worker able to launch a worker and receive its reply) was measured to one level, so a sub-coordinator's own children are workers, NOT a third tier. MEASURE your runtime before nesting deeper.

## §5 — Brief anatomy (a complete, self-contained assignment: 8 elements, each with the failure it prevents)
1. **The assignment + the standard of done.** The worker has no other source of intent.
2. **Read paths that point at the PRIMARY sources.** A coordinator's summary is a proxy; a worker acting on the proxy inherits the coordinator's errors and cannot detect them, while a worker reading the source catches what the summary lost. This single rule is what makes worker isolation an error FILTER instead of an error AMPLIFIER.
3. **A named destination for EVERY work product** (code included). An unwritten product evaporates when the worker ends — treat any product whose destination the brief does not name as a product that will not exist.
4. **A report cap.** Reports land in the coordinator's context, the scarcest resource. An uncapped report moves the worker's context problem onto the coordinator.
5. **A stop-when-stuck rule, VERBATIM in every brief:** *if errors recur, the approach stops converging, or you are about to change approach — stop and report what you found; do not thrash.* It bounds the cost of a wrong assignment and converts a blocked worker into evidence.
6. **The scope rule, VERBATIM** (§11).
7. **Persistence.** Write the brief to the store BEFORE launching — a brief held only in the coordinator's conversation dies with it; a persisted brief lets a crashed/replaced coordinator relaunch from the record.
8. **Proportionality.** The full anatomy is sized for non-trivial assignments; a one-line mechanical fan-out does not repay a persisted brief + stop rule. Keep the apparatus cheaper than the piece it governs.

FORM + BAR: elements 1–6 are the SIX SLOTS of a fill-in form the coordinator copies once per brief — assignment · read-paths (self-service) · write-path · report cap · stop rule verbatim · scope rule verbatim; 7–8 govern the brief rather than sitting in it. An EMPTY slot means NOT READY TO LAUNCH — that is the whole bar, and it is decidable without reading the brief for sense, which is what lets a check enforce it. Ship the contract at all three strengths, because a rule an agent must REMEMBER is weaker than a FORM it must fill in, weaker again than a CHECK that fires on its own: the prose above, a fill-in form your project supplies (projects running the planner-kit have it at `dev/briefs/_TEMPLATE.md`), and the deterministic backstop below.
DETERMINISTIC BACKSTOP (where your runtime offers one): two advisory checks, one per contract above — a LAUNCH gate naming any brief slot still unfilled as the launch goes out, and a COLLECT gate asking once for the outcome when a turn that gathered results names none; both only add a note and fail open, one environment variable silences them, and a REFUSING check is the right setting only where the guarded action is expensive and IRREVERSIBLE. CAVEAT — fixture-measured, NOT measured-working (§8's own efficacy rule): they pass a fixture matrix fired from installed copies, and no live session in an adopting project has fired either. CARRIER: on Claude Code the planner-kit ships them as `.claude/hooks/brief_gate.sh` (PreToolUse/Task) + `.claude/hooks/collect_outcome_gate.sh` (Stop), scoped by that kit to the project that installs it rather than by this skill.

## §6 — Steering semantics (MEASURE your runtime; do not assume it)
Correction semantics depend on the runtime. Measure two properties: (i) whether a message can reach a worker WHILE it runs, and at what granularity it arrives; (ii) whether a running worker's assignment can be REPLACED. Then apply the invariant: a correction that fits inside the existing assignment travels on whatever mid-run channel exists; a CHANGE of assignment is a new brief and therefore a new launch. A worker acts from its brief, so changing the goal without changing the brief leaves it on a stale specification. Where a runtime offers NO mid-run channel, every correction waits for collect — which costs at most one cycle, which is the reason to size cycles so losing one is affordable.
MEASURED INSTANCE (this project's runtime, recorded as an example of doing the measurement — yours may differ): a message to a running worker QUEUES and delivers at the worker's NEXT TOOL CALL (a live worker confirmed receipt + mid-task incorporation); a worker between tool calls or already finished sees the message only on resume. A REDESIGN still waits for a collect-time fresh launch. Background shell jobs are a third case — freely adjustable while they run. Use the mid-run channel for corrections / addenda / stop requests; keep complete briefs the norm (steering is course-correction, not design-by-drip).

## §7 — Capability tiering
Match worker capability to the reasoning DIFFICULTY of the piece: hard reading/design/code/judgment → top tier; synthesis/review/sweeps → middle; mechanical fan-out → cheapest. Overspending on mechanical work is waste; underspending on judgment work buys errors that cost more cycles than the saving. Rules that make it hold:
- **Tier empirically** — rank capabilities by measured performance on your OWN work, not by release order or vendor ordering.
- **Pin exact versions; NEVER an unversioned alias.** An alias resolves at launch to whatever is current, which can silently be a capability you excluded or never measured. Pinning makes the tier reproducible.
- **Exclude tiers with measured failure modes, and record the measurement.** (Illustration: a project that measured a newer model making more reasoning errors + jumping ahead of its evidence more than its predecessor excluded the newer one and locked its top tier to the predecessor at maximum reasoning. That exclusion rests on a measurement; a project that measures differently tiers differently.)
- **Coordinator authority is POSITIONAL, not capability-ranked** — the top tier is ALWAYS available to a worker for the hardest piece regardless of the coordinator's own level; the coordinator briefs, collects, and decides, and adjudicates what comes back by RECEIPTS (a fresh read/measurement for the claim), not by out-ranking the worker. (The former coordinator ≥ worker ordering is RETIRED.)
- **An excluded tier can return as a SUPERVISED tier, never as a free one.** The arrangement that re-admits it: a tightly-scoped WORKER (never a coordinator or a sub-coordinator) under an ACTIVE watch whose failure classes are NAMED in advance, launched through a dedicated project-scoped executor agent that carries the pin — so the capability is reached by ROUTE, not by naming it at the launch — with every completion logged, clean runs included, because a rate needs a denominator. (Illustration, this toolkit on Claude Code, 2026-08-04: the excluded tier returns ONLY as `delegate:opus5-executor` under a Planner's watch for scope-drift, thrash, and false-positive over-caution; `hooks/subagent_qa_gate.sh` logs every child completion to `dev/error_mode_log.jsonl`. Unversioned aliases stay excluded at EVERY scope, supervised included — an alias re-resolves silently, so it can never be a sanctioned route.)
- **Escalate the hardest judgment + writing deliberately.** Difficulty tracks reasoning demanded, not length; short high-stakes judgment is the most-often mis-tiered-downward.

## §8 — Verification (receipts)
- **Claims require receipts.** State a current fact only from a fresh read or measurement made for that claim. Recollection cannot be audited, and a description of a system drifts from the system as the system changes.
- **The author NEVER certifies their own gate-critical product.** A separate party with fresh context reviews it — the author's context holds the intent and reads that intent into the product; a reviewer holding only the product + the standard sees what is actually there.
- **Efficacy language has three levels, each with a price of admission:** *Built* → "attempted, untested". *Exercised against test cases* → "behaves as specified on these cases" (one level below working). *Measured before/after on real outcomes* → "improved", stated WITH the numbers. Without this, every status collapses into one undifferentiated label. Existence is the cheapest evidence and the most convincing-feeling, which is exactly why it needs an explicit rule against it.
- **Spend verification where a wrong claim changes a decision** — check a load-bearing claim at its source before a consequential decision; re-do none of the rest.

## §9 — The ledger system (three durable records, each closing a specific failure; each readable by a worker with no prior context)
- **Change ledger** — append-only, one dated row per change; past rows never edited. Closes the absence of a decision history (acute where there is no version control). Append-only is the operative property: a history that can be edited is indistinguishable from an accurate one.
- **Status ledger** — one row per capability/check, status from a FIXED vocabulary, every status past "attempted, untested" carrying a citation to the measurement that justifies it. Closes unfounded efficacy claims — an uncited status looks exactly like a cited one at the point of reading.
- **Code inventory** — one row per program (what it does, how invoked, where it came from, how verified). Every brief points its worker here BEFORE any code is written, in a fixed order: **USE** an existing entry where it fits · **ADAPT** one in place where it is close · **BUILD NEW** only where neither works · and REPORT which of the three was done. Closes reinvention — a second implementation of the same thing produces a second answer, and two answers that disagree cost more to resolve than either cost to build. **PERSIST-BY-DEFAULT:** a worker that writes ANY code persists it to the store before finishing (final versions in the durable area, iteration scratch in the scratch area) and NEVER discards it; disposal is the coordinator's triage call at collect, not the worker's. Tokens spent producing working code are an investment; code left in an ephemeral worker scratchpad is that investment thrown away.

## §10 — The two-stage quality protocol (for any product a standard covers only partly)
**Stage 1** runs the automated checks + specialist review passes — catches the mechanizable defects. **Stage 2** has the requester (or whoever owns the standard) mark up the stage-1 output; what they mark is the **residual** — what stage 1 could not catch.
- **Every residual item becomes a labeled test case**, carrying flagged text + corrected text. Converts a one-time human judgment into a repeatable check — the only ground truth for what automation misses.
- **The efficacy measure is the residual TREND across rounds, not the count in any one round.** A single round's count moves with how much material there was and how much attention the reviewer spent. Hold the counting rule fixed across rounds; record two figures alongside the count — total volume flagged, and the SHARE the standard covers. A residual that shrinks while its covered share rises means the material improved, not that attention lapsed.
- **Read the trend's SHAPE, not only its size.** When the residual falls, check whether what remains moved to a level automation cannot reach. (Measured in one project: a residual fell 61% in one round while the share visible to any automated check fell 28% → 0, and the round produced the first defect whose extent was a whole section rather than a sentence. That shape says build FEWER new checks and plan for a heavier reading pass — the opposite of what the falling count alone suggests.)
- **Remediation text is itself a defect source** (measured, not cautionary: in one round, four of nine flagged sites were text written in the previous round specifically to satisfy a previous instruction). Three rules follow: (1) **close a fix against the exact object the instruction named** (an instruction naming one figure, satisfied in a different figure + prose, left the named figure untouched and returned verbatim next round); (2) **sweep the CLASS, not the instance** (every class fixed everywhere fell to zero; a class fixed only at its flagged instance came back with ≥8 untouched siblings standing); (3) **re-audit newly-written text as a fresh draft** (text written to answer an instruction arrives after the checks ran and is exempt by default — compressing an abstraction produced an unhedged absolute the abstraction had carried the hedge for; cutting a self-important phrase left a sentence announcing a reason without giving one; removing a defect doing structural work leaves a structural hole — re-express what it carried rather than only deleting).

## §11 — Scope and safety
- **One explicit boundary, stated as a path/region, containing ALL work by every participant.** Nothing outside is read or written without an explicit per-excursion grant from the requester.
- **The boundary rule is repeated VERBATIM in every brief** — a fresh worker inherits nothing, so a rule held only in the coordinator's context never reaches the party that would violate it. (It exists because unbounded workers sweeping parent + system locations is OBSERVED behavior; containment is the reason for having a bounded work area at all.)
- **Read-only default outside the granted scope.**
- **Backup before bulk edits where no version control exists** — a dated archive at a known-good point is the only undo; a bulk edit has the widest blast radius and the highest cost to reverse, which earns it a mandatory precondition.
- **General form:** where the costs of being wrong are ASYMMETRIC, default to the cheap-to-reverse side and require an explicit token for the expensive side.

## §12 — What generalizes vs what is a local choice
**Load-bearing invariants** (hold on any runtime with isolated workers; removing one removes a property §1 paid for): coordinator that only decomposes/routes/synthesizes/verifies/decides; workers doing all domain work; code as co-equal, selected by the determinism test; everything exchanged persisted as a named record; complete self-contained briefs with primary-source reads + named destinations + report cap + stop rule; capability tiered by difficulty with versions pinned; the cycle ending in a re-fit decision with a fixed exit set; claims requiring receipts; no self-certification of gate-critical products; efficacy language gated on measurement; append-only provenance + a status ledger + a code inventory; an explicit boundary repeated in every brief.
**Invariants with a stated scope limit** (each depends on a runtime property — MEASURE it before carrying the rule): *the store is the only channel between participants* depends on workers being context-isolated (on a shared-live-memory runtime, persistence keeps its provenance value but stops being the only channel); *a change of assignment waits for the next launch* depends on workers not being re-assignable mid-run (where a worker can accept a new assignment while running, redirect it and drop the wait); *the full brief anatomy* is sized for non-trivial work; *a chunk can be routed whole to a sub-coordinator* depends on a worker being able to launch a worker and receive its reply — measured here to ONE level, so measure yours before nesting deeper.
**Free parameters** (choose for your context; do NOT import): specific capability tiers + version ids; boundary location; store layout + record naming; the names you give the arrangements; which checks are automated vs a reading pass; report-cap size; backup cadence; ledger formats + status vocabularies; the reviewer's identity in a build-then-review pair.
CLOSING RULE: implement each invariant with whatever primitive your runtime provides; where a rule names a runtime property, MEASURE that property rather than assume it — these rules were derived on one runtime, and the scope-limited four are exactly the places a different runtime changes the answer.
