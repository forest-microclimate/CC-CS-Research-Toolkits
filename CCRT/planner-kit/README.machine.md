WHAT THIS IS: planner-kit packages a portable operating system for running a multi-agent job from one project root — a supervisory loop (a planner that only decomposes / routes / synthesizes / decides; isolated worker subagents that do the domain work; code as a co-equal participant; a durable file store as the only channel between them), plus the standing disciplines that keep it honest: code-reuse + persist-by-default, two-stage quality detection, plan preservation, receipts-based verification, a project-structure standard (a known folder tree with one contract per folder), a Stale_Trash move-and-tombstone retirement discipline, and a collect-time capability-candidate duty. It deploys to ANY project root, anchors itself to that root (no absolute paths), and is content-agnostic about your project — by DEFAULT it installs two front-door files (the rules + `STRUCTURE_RULES.md`, the on-demand folder contract) plus two advisory workflow hooks, and the folder tree is materialized ON DEMAND as tasks need it; `--full` seeds the classic empty scaffolding up front. Either way it writes generic rules + empty structure, never your data.

PAIRING: the planner-kit ships INSIDE the CCRT at `CCRT/planner-kit/`. Install the CCRT ONCE into `~/.claude` (global agents/skills/hooks); run THIS kit's OWN `install.sh` separately in EACH project root that adopts the supervisory workflow (it writes the project-level CLAUDE.md contract + hooks + the model-routing set; upgrades: re-run with `--upgrade-rules`). The two installers are DELIBERATELY separate — global capability vs per-project workflow — and are designed to be used together.

## What the installer does (and never does)
It operates on the CURRENT directory (your project root). By DEFAULT (minimal) it installs the two front-door files plus the two advisory hooks; `--full` adds the classic scaffold + seeds. Behaviors:
- BOTH MODES — ROOT `CLAUDE.md`: if ABSENT, create it (payload rules wrapped in planner-kit markers); if PRESENT WITHOUT the marker, APPEND the rules block behind `<!-- planner-kit:BEGIN … -->` … `<!-- planner-kit:END -->`, leaving your existing content byte-for-byte unchanged; if the marker is ALREADY present, no-op ("already installed"). It also seeds `.claude/CLAUDE.md` as a ≤2-line pointer stub, only if absent. If a planner-kit marker is found INSIDE `.claude/CLAUDE.md` (a v1 install), it prints migration advice and leaves that file untouched.
- BOTH MODES — install `.claude/hooks/brief_gate.sh` + `.claude/hooks/collect_outcome_gate.sh` (mode 755, only if absent) and register them in `.claude/settings.json`: seeded if that file is absent, otherwise DEEP-MERGED via `lib/merge_settings.py` so your keys and any foreign hook survive byte-for-byte, keeping a dated `.pre-planner-kit-<date>` copy before the first merge. Existing hook entries dedup by command, so a re-run is a no-op. Both hooks advise only and fail open; `PLANNER_KIT_HOOKS=off` silences them.
- BOTH MODES — seed `STRUCTURE_RULES.md` at the project root ONLY IF ABSENT, recording this kit's absolute path into its SEEDS section (so an on-demand materialization can find the seed templates).
- BOTH MODES — seed the MODEL-ROUTING SET (v1.4, only-if-absent): `.claude/agents/{fable-executor,opus5-executor}.md` + `.claude/skills/model-verification/{SKILL.md,model_run_audit.py}`.
- `--upgrade-rules` (v1.4) — replace the FIRST planner-kit BEGIN..END span in the root `CLAUDE.md` with the current rules block IN PLACE: dated backup kept first, bytes outside the span untouched, summary records `upgraded (vOLD -> vNEW)`; REFUSES when no block exists. Composes with `--dry-run`.
- `--full` ONLY — (a) SCAFFOLD the standard working dirs via `mkdir -p` (idempotent): `src/ dev/ dev/briefs/ dev/tools/ documents/ data-outputs/{source-immutable,intermediate,products}/ plots-figures-tables/ sandbox/ backups/ Stale_Trash/ plans/{current_active,for_later_resume,finished}/ .claude/agent-memory/planner/`, dropping a `.gitkeep` into each created dir that stays empty (harmless without git; on a re-run the `.gitkeep` makes the dir non-empty, so nothing is re-added); and (b) SEED the ledger templates + planner memories + `dev/tools/stale_move.sh` ONLY IF ABSENT. In the DEFAULT minimal mode these dirs/seeds are NOT created — the agent materializes them on demand per `STRUCTURE_RULES.md`.
- (d) print a did/skipped summary table (plus the migration note when relevant).
- (e) ZERO deletes, ZERO overwrites. A re-run changes nothing it already did; `.DS_Store` is never copied.
It NEVER deletes a file, overwrites an existing file, or writes outside the current project root. It refuses to run if the current directory is the kit itself OR anywhere inside the kit tree (the `payload/` subdir included) — so it can never append its own source `CLAUDE.md` to itself.

## Marker / merge semantics
The block the installer manages inside your ROOT `CLAUDE.md` is delimited by:
    <!-- planner-kit:BEGIN v1.4 installed=YYYY-MM-DD -->
    … the planner-kit rules …
    <!-- planner-kit:END -->
Detection keys on the `<!-- planner-kit:BEGIN` prefix, so once ONE such block is present the rules merge is a no-op (the installer never rewrites your `CLAUDE.md`). Everything OUTSIDE the block is yours and is never modified. To update the block by hand, edit between the markers; to re-install fresh, delete the whole block (markers included) and re-run. The `.claude/CLAUDE.md` pointer stub carries NO marker, so the installer never mistakes it for an installed rules block.

VERSION-MISMATCH UPGRADE (migration). The merge stays a no-op regardless of the present block's version, but the installer is NOT silent across versions: a SAME-version block reruns quietly, whereas a block from a DIFFERENT kit version now prints a loud `WARNING (planner-kit version mismatch)` naming the found vs current version. Why it matters: an older block will not carry this version's references (e.g. the `STRUCTURE_RULES.md` pointer added in v1.2), so a freshly seeded `STRUCTURE_RULES.md` can sit UNREFERENCED beside it. The installer never edits your file un-asked. REMEDY (to upgrade): re-run the installer with `--upgrade-rules` (v1.4 — replaces the block in place, dated backup kept first), or delete the whole `planner-kit:BEGIN … planner-kit:END` block by hand and re-run without flags. (A version-less manual drop-in — `<!-- planner-kit:BEGIN -->` with no version token — is treated as a match and warns nothing.)

## Git layer (recommended — optional)
The standard works with or without git; for a combined code+research project git is recommended, and the scaffold's `.gitkeep` files exist so the empty standard dirs survive the first commit. A portable setup:
- `git init` at the project root.
- Set a REPO-LOCAL identity so this project's commits carry the account you intend (not your machine's global default): `git config user.name "Your Name"` and `git config user.email "you@example.com"`. The origin-project policy is a DEDICATED per-project email set repo-locally (never `--global`), which keeps this project's commits cleanly separated from your personal ones — substitute your own address; no real address ships in this kit.
- `.gitignore` suggestions: `.DS_Store`, `sandbox/`, `backups/` (dated zips are large binaries), and `settings.local.json` (Claude Code local settings — Claude Code ignores it already).
- COMMIT the operating context so it travels with the repo (origin-project adopted policy): the whole `.claude/` tree (settings / agents / skills / rules) AND `.claude/agent-memory/` AND `Stale_Trash/` (retained history) — everything except the gitignored paths above.
- Initial commit = the current tree. NO remote / push until you decide to add one (a separate, deliberate step).

## Honest efficacy
These principles were derived and MEASURED in one origin project; the numbers cited in `docs/` are that project's. The principles are portable, but their efficacy in YOUR project is unmeasured until you measure it — treat every rule as attempted-untested here until a run in your project yields a before/after number. The v1.1 project-structure standard, the v1.2 lazy-scaffold redesign, the v1.3 produced-file slimming, and the v1.4 model-routing set + `--upgrade-rules` upgrade path are likewise attempted-untested until a project adopts them (the installer is fixture-measured — it behaves as specified across its build test cases, the v1.4 additions across a 17-assertion red-before-green suite — but not yet measured-working in a real adopting project). That discipline is itself one of the rules (see the EFFICACY_LEDGER template).
