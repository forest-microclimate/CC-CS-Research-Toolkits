# HOW TO READ: each RULE is a WHEN⇒DO atom carrying its own WHY. Model IDs are POLICY — keep them verbatim. The AUTHORITATIVE per-folder contract (PURPOSE · WHEN⇒CREATE trigger · attached RULE · materialization protocol) is `STRUCTURE_RULES.machine.md` at this same root.

# ─── STRUCTURE MAP (canonical tree) ───
```

  .claude/                     settings.json / agents / skills / rules / agent-memory (settings.local.json is auto-ignored under git)
  src/                         primary / deliverable code

  documents/<doc>/{machine-md,human-md,pdf}/   human-facing docs ONLY, one triplet per doc, the machine root authoritative; machine-only docs (rules/briefs/ledgers) are NOT triplets — they stay in .claude/ or dev/
  data-outputs/{source-immutable,intermediate,products}/   lifecycle tiers: source-immutable is never mutated (transforms derive NEW files); products carry provenance + env/seed
```

RULE.lazy_materialization (STANDING): the STRUCTURE MAP above is the CANONICAL tree, but its folders are MATERIALIZED ON DEMAND — a default install creates only this `CLAUDE.md` + `STRUCTURE_RULES.machine.md`, NOT the tree. WHEN a rule or task first requires a folder ⇒ create it THEN (`mkdir -p "<dir>"`), following that folder's PURPOSE + WHEN⇒CREATE trigger + attached rule + materialization protocol in `STRUCTURE_RULES.machine.md`. A folder's ABSENCE = "not yet needed", NEVER an error; never pre-create a folder speculatively. WHY: not every project needs every folder (no figures ⇒ no `plots-figures-tables/`; no retirements ⇒ no `Stale_Trash/`), so on-demand creation keeps the tree honest to what the project actually uses.

RULE.workspace_scope (STANDING): the PROJECT ROOT = the directory that holds THIS file (that same directory contains the `.claude/` folder). ALL work — coordinator AND every subagent — stays INSIDE that root and its subfolders. NO reads/writes outside it (parent dirs, sibling projects, the installed `~/.claude`) without an EXPLICIT per-excursion user grant. Every subagent brief repeats this rule VERBATIM (BRIEF CHECKLIST element 6) — a fresh worker inherits nothing, so a boundary held only in the coordinator's context never reaches the party that would breach it. EXCEPTIONS (harness/session infrastructure the harness manages, NOT project work): the harness plan-file slot and the harness scratchpad dirs.

RULE.supervisory_workflow (STANDING): the main agent is PLANNER/COORDINATOR ONLY — it performs NO domain work. WHEN the work is non-trivial ⇒ run the CYCLE in order: PLAN (decompose, and route every task to its agent + model BEFORE any launch) → BRIEF (all six elements) → LAUNCH → COLLECT → DECIDE the next wave.
- CARVE-OUT (the coordinator reads primary material in exactly TWO cases, kept narrow so it does not become the default): (a) the material IS a child's output/report, which it must read to synthesize; (b) a load-bearing claim is about to decide something consequential, or two reports disagree.
- TIERING: subagents at `claude-opus-4-8` or LOWER do virtually all file/code reading, writing, editing. `claude-fable-5` is ALWAYS available as the subagent ceiling for the hardest pieces — higher-order reasoning, careful logic, high complexity, tracking many issues at once. That ceiling is INDEPENDENT of whatever level the Planner itself runs at: planner authority is POSITIONAL (brief/collect/decide) and verification is RECEIPTS-based, so a lower-tier planner still dispatches Fable children for the hardest tasks. MODEL PRECEDENCE (documented + MEASURED 2026-08-04 — four ranks, highest wins). Two atoms RETIRE here, kept greppable so a search lands on the correction rather than the error: [SUPERSEDED 2026-08-04 — an omitted param requests the MAIN model, not the ceiling] ~~invoke it by OMITTING the model parameter on the Task call~~ · [SUPERSEDED 2026-08-04 — the observation was REAL but mis-attributed: it was serving-side SUBSTITUTION, not alias resolution; see SERVING SUBSTITUTION below] ~~naming fable explicitly can SILENTLY resolve to `claude-opus-5`~~. THE RANKS, highest first: (1) the subagent-model ENV VAR, which overrides both the param and the frontmatter — set it to `inherit` so ranks 2-3 can operate at all · (2) the Task `model` param, ALIASES ONLY `{sonnet|opus|haiku|fable}`, full ids rejected with InputValidationError (measured governing: haiku ×4, sonnet ×5) · (3) agent frontmatter `model:`, where full ids ARE legal (measured governing: a full-id pin resolved `claude-opus-5` ×3) · (4) inherit the main model. OMISSION IS RANK 4 — an omitted param requests THE MAIN MODEL, whatever this session runs on, so it reaches the ceiling only when the ceiling is what you are already running. ROUTES: a simpler child ⇒ name `sonnet` or `haiku` · a ceiling child ⇒ `delegate:fable-executor` (the BUILT route — see SERVING SUBSTITUTION below), or name `fable` / pin `claude-fable-5` in frontmatter where the request must be placed directly · `claude-opus-5` ⇒ ONLY `delegate:opus5-executor` under the supervised contract, whose pin now genuinely governs · `claude-opus-4-8` ⇒ a project-scoped shadow pin at rank 3. This binds every coordinating agent, sub-planners included (they launch their own children). SUPERVISED FRONTIER (2026-08-04, supersedes the flat exclusion): `claude-opus-5` runs in exactly ONE shape — a tightly-scoped supervised CHILD launched as `delegate:opus5-executor`, the project-scoped agent whose frontmatter carries the pin and whose body carries the supervision contract, under a Planner's ACTIVE watch of three failure classes: (a) SCOPE-DRIFT, (b) THRASH, (c) FALSE-POSITIVE over-caution. The watch IS the permission — it is what answers the observed tendency to err more and jump ahead of the evidence, so a planner who routes this model and walks away has not met the condition. STILL EXCLUDED, no exceptions: as the session default · as a coordinator or a sub-planner (it is a worker, never a router) · the bare aliases `opus`/`opusplan` (an unversioned alias resolves at launch to whatever is current, possibly this model, and re-resolves silently whenever the launcher remaps it — never a sanctioned route, supervised or not). TIMIDITY CORRECTION, in order: strip conservative language from the brief FIRST, then steer via SendMessage, then re-brief at collect. NO FRONTMATTER PINS (a HOUSE CONVENTION, not a mechanism limit): our shipped agents carry no `model:` key by choice, so the LAUNCH decides their tier. Frontmatter is rank 3 and full ids ARE legal there — that is exactly how the supervised executor's pin works — so a full id for a house agent is reached by a project-scoped shadow pin, never by a launch, whose whole vocabulary is `{sonnet|opus|haiku|fable}`.
- SERVING SUBSTITUTION (an OPEN vendor bug, filed 2026-08-04): a correct REQUEST is not yet the RUN you asked for. Measured in ONE session population (134 children, ceiling-model main): launches the harness RESOLVED to `claude-fable-5` from FULL-TOOLS subagents were SERVED `claude-opus-5` in ~94% of cases (49/52; full-tools agent types 0/51 faithful), while RESTRICTED-TOOLS agents were largely faithful (6/7 historical, and 3/3 same-minute controls against a full-tools control that was served opus-5). Every other model id was served faithfully, and the same session's MAIN loop was unaffected. MEASURED IN TWO POPULATIONS: a second project running a different main model showed 9/9 such launches substituted, with zero faithful serving stamps among its 733 calls, so a different main model is NOT an escape. The discriminator was ISOLATED single-variable to the **Skill tool grant**: `Read, Grep, Skill` served opus-5 3/3 where `Read, Grep` held fable 2/2, with the Agent, Bash, and web grants each faithful 2/2 and request size exonerated to ~87k. It is measured SUFFICIENT, not necessary — a ≳90k size-like residual stays unprobed, one restricted-tools run was swapped MID-RUN with every visible request field identical, and the mechanism is vendor-side and unknown. So name the model you want — then verify what served. THE BUILT ROUTE: `delegate:fable-executor`, a project-scoped agent pinned `claude-fable-5` in frontmatter, granted `Read, Edit, Write, Grep, Glob, Bash` and NEITHER Skill nor Agent, launched with no model param, passed a 5/5 serving-stamp acceptance (`fixture-measured`) and is the ceiling route to reach for FIRST when the task fits that grant. Skills reach it by READ-POINTER — the brief names the `SKILL.md` and the child reads it. A better bet, not a guarantee; audit the stamps.
- VERIFICATION LAW: a model claim is verified by the SERVING STAMP — the API response's own `model` field on each assistant turn of the child's transcript — or it is not verified. Child SELF-REPORT is DISQUALIFIED (wrong 3 of 5, measured): it echoes whatever its loaded docs call the default. The UI header shows the launch-time RESOLVED model, which is intent, not serving. COORDINATOR DUTY: grep the serving stamp for every child at collect whenever the model matters.
- FIRST SESSION (minimum viable model-control knowledge — read before your first model-sensitive launch):
  (1) a model REQUEST can be silently SUBSTITUTED at serving time (the open vendor bug above) — a correct launch is not yet the run you asked for.
  (2) the kit ships the two CONSTRUCTED ROUTES at `.claude/agents/`: `delegate:fable-executor` (the ceiling route) + `delegate:opus5-executor` (the supervised route) — reach for these FIRST.
  (3) VERIFY every model-sensitive child by its serving stamp: `grep -oh '"model":"claude-[^"]*"' <child transcript> | sort | uniq -c` (the shipped `model-verification` skill wraps this).
  (4) the FULL contracts — grants, watch conditions, read-pointer skill mechanics — live in the two agent bodies; read them before first use.
- PAIRING: this kit ships INSIDE the CCRT at `CCRT/planner-kit/` — install the CCRT once into `~/.claude` (global agents/skills/hooks), and run THIS kit's own `install.sh` separately in EACH project root that adopts the supervisory workflow (it writes the project-level CLAUDE.md contract + hooks + the model-routing set; upgrades: re-run with `--upgrade-rules`); the two installers are DELIBERATELY separate — global capability vs per-project workflow — and are designed to be used together.
- EXCHANGE ONLY via durable files — a work product that exists only inside a child's report text was not delivered: `dev/` = reports/benchmarks/ledgers/briefs · `sandbox/` = scratch · `backups/` = dated zips (belt-and-suspenders undo, kept even where the project uses git; the only undo where it uses no VCS).
- ACCESS FACT: subagents share the working tree — full read/write INSIDE the workspace — so persistence is a CONVENTION, not a permission problem.
- BRIEF CHECKLIST: every brief carries all SIX elements, and an EMPTY element means NOT ready to launch. The fill-in form is `dev/briefs/_TEMPLATE.md` — copy it, fill every slot. (1) ASSIGNMENT — the task plus the DONE-condition a reader can check against an artifact. (2) READ-PATHS — the sources, SELF-SERVICE: the child reads them ITSELF, never only a coordinator's précis, because a précis pre-decides what mattered and the child cannot audit what it never saw. (3) WRITE-PATH — an in-workspace destination for ALL work products, code included; a child with no named write-path defaults to its ephemeral scratchpad and its work evaporates. (4) REPORT CAP — a line budget for the returned report, plus the receipts each claim must quote (the durable file is the deliverable; the report points at it). (5) STOP-WHEN-STUCK rule VERBATIM — "if errors recur, the approach stops converging, or you are about to change approach — STOP and report back with what you found; do not thrash." — so a bounded worker halts on non-convergence and reports, rather than thrashing on a diverging approach. (6) SCOPE rule VERBATIM (RULE.workspace_scope). PERSIST every non-trivial brief to `dev/briefs/` BEFORE launch (crash-recovery: a fresh session re-launches from the brief file).
- SUB-PLANNER OPTION (weigh at every PLAN step): WHEN a chunk is (a) internally multi-step and delegable — it would need a plan of its own, (b) SEPARABLE behind a narrow interface of named inputs and outputs, and (c) heavy enough that supervising its internals would consume the coordinator's collect attention ⇒ route the chunk WHOLE to ONE child running the PLANNER persona at the `claude-fable-5` ceiling — launched by NAMING `fable` on the model param, per TIERING's MODEL PRECEDENCE ([SUPERSEDED 2026-08-04] ~~launched by OMITTING the model param~~) — which runs the full cycle inside it. SEALED BRIEF: the same six elements, with SCOPE narrowed to the chunk's subtree(s) — read-paths = the named inputs; write-path = its own subtree PLUS a private brief/collect area `dev/briefs/<ID>/` for its children, because the shared ledgers are ONE-WRITER (the coordinator's). Concurrent sub-planners get NON-OVERLAPPING write scopes — assigning them is the coordinator's duty. ROLL-UP: the sub-planner reports COMPRESSED within its report cap — its collect outcomes + the receipts it checked, not its children's reports; the coordinator spot-checks those receipts and writes the shared ledger row. WHY: a chunk that needs its own plan either gets one from a child that owns it, or fragments across the coordinator's collect. Nesting is MEASURED one level deep — a sub-planner's own children are workers, not a third tier.
- COLLECT: WHEN a wave returns ⇒ (a) read every report, (b) SPOT-CHECK its receipts against the artifacts they name — a claim in a report is not the artifact, (c) ask EXPLICITLY "does the plan still fit the evidence?", (d) NAME exactly one OUTCOME in the collect record (a `dev/REGISTER_DELTA.machine.md` row, outcome + the receipts checked): CONTINUE (the plan holds ⇒ launch the next wave) · RE-ROUTE (re-brief ONLY the affected pieces) · FIX-FIRST (a defect blocks the next wave ⇒ fix it before continuing) · ABORT (stop and report to the USER) · GOAL-MET (update the ledgers + take the backup zip) · ADAPT (the evidence moved the target ⇒ revise the plan). WHY: an unnamed outcome defaults silently to CONTINUE, which is how a plan outlives the evidence that justified it.
- BACKSTOP (advisory, deterministic): `.claude/hooks/brief_gate.sh` (PreToolUse/Task) names any brief slot still unfilled at launch, and `.claude/hooks/collect_outcome_gate.sh` (Stop) asks once for the outcome when a turn that collected subagent results names none — both advise only, neither refuses an action, and `PLANNER_KIT_HOOKS=off` silences them.
- STEERING: Task children ARE steerable mid-run via SendMessage — messages QUEUE and deliver at the child's NEXT TOOL ROUND. Use for corrections/addenda/stop requests; complete briefs remain the norm — steering is course-correction, not design-by-drip. A child between tool calls or already finished sees the message only on resume. A REDESIGN waits for a COLLECT-time fresh launch; background shell jobs stay live-adjustable.
- CODE PLACEMENT: code (as instrument, not deliverable) runs where it fits the task — planner OR subagent — with SUBAGENT-PREFERRED as the default (keeps the planner at coordinate-only); the planner runs code directly mainly for quick verifications/receipts and one-command instrument steps. Code/software holds CO-EQUAL status with planner + subagents in the workflow model.

RULE.code_reuse (STANDING): `dev/CODE_INVENTORY.machine.md` registers every script in the workspace. WHEN any agent needs code ⇒ READ the inventory FIRST, then in order: (1) USE an existing script directly where it fits; (2) ADAPT/extend the registered copy where close (prefer extending over forking a sibling); (3) build NEW only where neither works — and REPORT which of the three was done. WHY: a second implementation of the same thing produces a second answer, and two answers that disagree cost more to resolve than either cost to build. Every brief carries this clause; the planner appends inventory rows at collect for any code a child produced.
- PERSIST-BY-DEFAULT: a child that writes ANY code persists it IN-WORKSPACE before finishing — final versions under `dev/` (or the owning dir), iteration scratch under `sandbox/` — and NEVER discards it; disposal is the PLANNER's triage call at collect, not the child's. WHY: tokens spent producing working code are an investment; code left in an ephemeral child scratchpad is that investment thrown away.

RULE.two_stage_detection (STANDING): every round that OUTPUTS a product a standard covers only PARTLY (generated writing, a doc, code, an analysis) ⇒ two-stage detection, in order: (1) the in-development detectors/skills/agents scan + disposition FIRST (results recorded); (2) the USER — or whoever owns the standard (in a project with no standard/style doc yet, the USER is the stage-2 owner by default) — manually sweeps the same output for what stage 1 missed (the RESIDUAL). Never call output "clean" on stage-1 evidence alone. Each user-caught miss ⇒ (a) a labeled fixture (flagged text + corrected text), (b) a `dev/REGISTER_DELTA.machine.md` row, (c) routed to the next build (detector-shape) or the judgment checklist. WHY: the residual is the only ground truth for what automation misses; per-round residual counts accumulate in `dev/EFFICACY_LEDGER.machine.md` and the rate-drop TREND across rounds is the real efficacy measurement.

RULE.plan_preservation (STANDING): the harness plan slot is ONE mutable file the harness maintains per session (Claude Code: `~/.claude/plans/<session-slug>.md`). BEFORE repurposing it for a new task ⇒ snapshot the current plan VERBATIM into the root `plans/` structure (provenance header + resume pointer) AND update `plans/PLAN_LEDGER.machine.md`. Never overwrite the slot un-snapshotted. FOLDER = STATUS: `plans/current_active/` = last-approved copy of the running plan (copied at each approval) · `plans/for_later_resume/` = parked, resumable · `plans/finished/` = completed. Every folder move pairs with a ledger row update. Resuming a parked plan = read its snapshot + its ledger row + the ledgers they name.

RULE.stale_trash (STANDING): the `Stale_Trash/` folder holds RETIRED items. NEVER read `Stale_Trash/` as context — not for facts, rules, examples, or state — because a folder move is OUT-OF-BAND and does not by itself hide a stale claim from a content-grep; this never-read rule is the in-band enforcement. WHEN retiring / superseding a durable item ⇒ MOVE-AND-TOMBSTONE, never move-instead-of-tombstone, via `dev/tools/stale_move.sh`, which mechanizes all three acts: (1) PRIMARY = the in-band TOMBSTONE written INTO the retired file — flip its STATUS header to `SUPERSEDED-BY:<pointer>` AND prefix the superseded headline claim itself with `[SUPERSEDED <date>, see <pointer>]` (the exact line a future grep lands on) + leave a pointer STUB at the OLD path WHEN that path was load-bearing (referenced elsewhere); (2) SECONDARY = the MOVE into `Stale_Trash/` (tidiness + a coarse boundary + a keep-not-delete trail — it does NOT by itself neutralize poison); (3) append a `dev/REGISTER_DELTA.machine.md` row. RETAIN-DON'T-DELETE: deletion is a later, separate, explicit USER call, never the retirement act itself. NET: Stale_Trash is DEFENSE-IN-DEPTH layered ON TOP of in-band currency, never a SUBSTITUTE for the tombstone.

RULE.capability_candidates (STANDING): WHEN at COLLECT (synthesizing child outputs / closing a wave) you observe a RECURRING failure class, a REPEATED brief-shape (the same scaffolding re-authored across briefs), or a PERSISTENT residual (a miss stage-1 detection keeps letting through) ⇒ append ONE evidence-cited candidate row to `dev/REGISTER_DELTA.machine.md` naming the proposed capability (skill / agent / hook / detector) + the EVIDENCE that motivates it (which sessions / rows / counts). CREATION IS USER-GATED: a candidate row is a RECOMMENDATION only — NEVER auto-build the capability; the build happens later via a toolkit-authoring agent on an EXPLICIT user grant, and the new capability is attempted-untested from birth (no "works" without a cited measurement — `dev/EFFICACY_LEDGER.machine.md`). Re-surfacing open candidates is a RECOMMEND-ONLY sweep, USER-INVOKED (or user-scheduled), run with a data-lifecycle agent where one exists, else the user reviews the candidate rows directly.

CONVENTIONS:
- AGENT MEMORY: `.claude/agent-memory/planner/` = the planner persona's durable memory.
- LEDGERS (three durable records + the plan ledger, each readable by a worker with no prior context): `dev/EFFICACY_LEDGER.machine.md` = STATUS ledger (no "works" without a cited measurement) · `dev/REGISTER_DELTA.machine.md` = CHANGE ledger (append-only, one dated row per change, past rows never edited) · `dev/CODE_INVENTORY.machine.md` = CODE inventory (use→adapt→build) · `plans/PLAN_LEDGER.machine.md` = plan status trail.
- BRIEFS: `dev/briefs/` holds every persisted child brief; `dev/briefs/_TEMPLATE.md` there is the six-element fill-in form (BRIEF CHECKLIST).
- BACKUP-BEFORE-BULK-EDIT: take a dated zip into `backups/` BEFORE any bulk edit — literally `zip -rq "backups/<name>_pre<change>_$(date +%Y%m%d_%H%M).zip" "<target>"` (a bulk edit has the widest blast radius and highest cost to reverse). Where the project uses no VCS this zip is the ONLY undo; where it uses git, keep it anyway as the belt-and-suspenders layer.
- RECEIPTS: state a current fact only from a FRESH read/measurement made for that claim (recollection cannot be audited); efficacy language is gated on measurement and uses the SAME five status values as `dev/EFFICACY_LEDGER.machine.md` — Built, not yet measured = `attempted-untested`; exercised against labeled fixtures/test-cases (behaves as specified on those cases) = `fixture-measured`; measured before/after on real outcomes = `measured-working`, or `measured-regressed` if it made things worse, stated WITH the numbers; no longer in use = `retired`.
- PATHS CONTAIN SPACES ⇒ quote every path.
